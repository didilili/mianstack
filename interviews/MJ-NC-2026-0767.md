> 小天才 AI 应用工程师（穿戴）一面面经27届校招｜企业内部 Coding Agent 平台方向
>
> # ============================================================ 一、岗位定位与面试概况
>
> 分享一下今天的小天才 AI 应用工程师（穿戴）技术一面。
>
> 【岗位定位】这个岗位主要是做企业内部的 AI Coding 平台，而不是传统 Java 后端开发，也不是直接开发儿童手表上的 AI 助手。
>
> 根据 JD 和面试交流，岗位主要围绕 Coding Agent、测试 Agent、MCP/CLI 工具链、上下文管理、Agent 评测，以及 AI 在研发流程中的实际落地展开。
>
> 虽然岗位名称带有“穿戴”，但实际工作更偏向利用 AI 提升穿戴产品相关的软件研发效率，包括探索面向内部研发人员的 AI 开发工具和应用生成平台。
>
> 【个人背景】27 届人工智能专业本科生，有两段 Java 后端实习经历。个人项目主要是基于 LangChain4j、LangGraph4j 的智能网页创作平台，平时也经常使用 Claude Code、Codex、Pi Agent 等 AI Coding 工具。
>
> 【整体面试体验】面试官比较专业，主要围绕 Agent 项目、Coding Agent 设计以及 AI 工程化实践深入交流。
>
> 基本没有传统 Java 八股和算法题。面试重点是：是否真正开发过 Agent，是否理解 Coding Agent 的工作机制，以及能否将已有技术迁移到企业内部 AI 研发平台。
>
> 说明：以下内容根据会议记录整理，部分问题并非面试官原话。
>
> # ============================================================ 二、智能网页创作平台项目（重点深挖）
>
> 1. 介绍一下你的 Agent 项目，为什么要做？
>
> 个人 Demo，主要参考美团 NoCode 平台，希望通过实际开发理解 AI Coding 平台的设计思路。
>
> 后端和 Agent 工作流由自己开发，前端主要借助 AI Coding 工具完成。
>
> 1. 假设用户提出一个网页生成需求，从输入到最终生成，完整流程是什么？
>
> 主要介绍了两种生成模式：普通生成模式和工作流模式。
>
> 工作流包含需求分析、Prompt 增强、并行素材收集、复杂度路由、代码生成、质量检查和工程构建。
>
> 根据需求复杂度选择生成普通 HTML 页面或 Vue 项目。
>
> 1. 为什么需要 Prompt 增强？
>
> 非技术用户描述的需求通常比较模糊。
>
> 通过 Prompt 增强，将用户需求转换为包含页面结构、技术栈、功能要求和视觉风格等约束的具体开发任务。
>
> 同时可以结合收集到的开源素材，提高生成质量。
>
> 1. 为什么选择 LangGraph4j？
>
> 主要用于工作流节点编排、条件路由和质检反馈。
>
> LangChain4j 负责模型调用、工具集成等基础能力，LangGraph4j 负责工作流的执行逻辑。
>
> 1. 质量检查节点具体做什么？失败后如何处理？
>
> 目前主要分为构建结果检查和规范约束检查。
>
> （1）构建结果检查：当前实现中，构建失败会直接结束。（2）规范约束检查：规范不符合要求时，将问题反馈给生成节点进行修复，最多重试三次。
>
> 面试官继续追问质检深度。
>
> 如实说明目前主要是基础规范检查，还没有完善的页面交互、布局质量和审美评测体系。
>
> 1. 如果用户在生成后手动修改了代码，下一轮 Agent 修改时如何避免覆盖这些改动？
>
> 这道题比较有挑战。
>
> 当前项目支持多轮修改，但还缺少完善的代码变更基线管理。
>
> 如果继续完善，需要基于当前代码状态进行增量修改，并考虑版本管理、Diff 和用户修改保护，而不是重新生成整个项目。
>
> 1. 为什么采用单 Agent 工作流，不使用多 Agent？
>
> 当前业务流程比较明确，单 Agent 配合预定义工作流已经可以满足需求，整体更容易管理，成本也较低。
>
> 多 Agent 可以进行任务拆分和并行协作，但也会增加上下文传递、状态同步和协调成本。
>
> 1. Agent 工具调用和流式输出有什么技术难点？
>
> 主要讨论了普通文本生成和 Vue 工程生成的差异。
>
> 普通文本可以直接流式输出，而工程生成涉及 Function Calling，需要处理工具调用过程和执行状态的推送。
>
> 开发时遇到过框架工具调用回调适配问题，通过阅读源码和相关 Issue/PR 进行排查解决。
>
> 1. 如何保证 Agent 工具调用安全？
>
> 主要从两个层面考虑：
>
> （1）Prompt 层：明确执行约束，防范提示词注入。（2）Runtime 层：限制文件访问范围、工具权限、参数格式以及危险操作。
>
> 核心思想是不能假设模型始终可靠，关键权限必须由程序强制控制。
>
> # ============================================================ 三、Agent 工程化和评测
>
> 1. 如果你的 Agent 要推广到团队使用，还缺少什么？
>
> 目前主要是个人 Demo，缺少完善的质量评测和运行监控体系。
>
> 如果用于真实研发场景，需要增加任务成功率、失败率、工具调用次数、Token 消耗、执行耗时等指标。
>
> 对于代码修复等客观任务，可以通过测试验证；对于网页美观程度等主观任务，还需要人工评价和用户反馈。
>
> 1. Workflow 和 Agent Loop 有什么区别？
>
> Workflow 的节点和允许执行的路径主要由开发者预先定义，更加可控。
>
> Agent Loop 由模型根据当前任务和工具执行结果动态决定下一步，更加灵活。
>
> 实际系统也可以结合两种方式。
>
> # ============================================================ 四、中控智能体实习经历
>
> 1. 介绍一下你在实习中开发的智能体。
>
> 主要面向智能驾培中控系统，通过自然语言查询学员训练、车辆等业务数据。
>
> 使用 OpenClaw，通过容器部署并接入现有 Java 后端。
>
> 1. 用户发起一个查询请求，完整链路是什么？
>
> 用户在前端输入自然语言需求，请求到达 Java 后端，再由后端调用 Agent 服务。
>
> Agent 根据 Skill 选择业务 API 或预定义查询脚本，获取结果后整理为自然语言，最终返回前端。
>
> 1. 为什么同时使用业务 API 和固定脚本两套链路？
>
> 主要考虑业务适配和数据安全。
>
> 能通过现有 API 完成的查询直接复用接口。
>
> 对于需要查询数据库的场景，预先编写脚本，由模型负责提取参数和选择工具，不允许自由生成并执行任意 SQL。
>
> 这样能降低错误查询、SQL 注入和高开销查询风险。
>
> 1. Skill 是怎么开发、调试和优化的？
>
> 根据具体业务需求编写 Skill，定义调用条件、输入参数、输出格式和约束。
>
> 例如模型容易输出错误字段名，就在 Skill 中约束输出结构，再通过历史业务场景回归验证。
>
> 1. AI Coding 如何理解历史代码中的隐性约束？
>
> 分享了 AGENTS.md、项目知识库以及相关插件的使用经验。
>
> 例如项目中有特殊的接口路径约定，模型不了解时容易重复拼接路径。
>
> 可以将这些规则沉淀为项目知识，并在开发前加载必要上下文，减少重复出错。
>
> # ============================================================ 五、中科软实习中的 AI Skill
>
> 1. 你将保险规则配置流程沉淀为 Skill，具体怎么做的？
>
> 以重大疾病相关配置为例：
>
> 先人工理解保险产品条款，整理结构化配置要求。
>
> 再由 AI 结合现有字段和业务规范生成 SQL 配置语句，最后人工检查字段、去重和业务正确性。
>
> 强调 AI 主要用于减少重复劳动，不能直接自由操作生产数据库。
>
> # ============================================================ 六、大模型基础与 RAG
>
> 1. 什么是大模型幻觉？为什么会产生？
>
> 从语言模型的概率预测机制、训练数据不完善和上下文不足等角度回答。
>
> 主要缓解方案包括 RAG、外部工具查询和结果校验。
>
> 1. RAG 的完整流程是什么？
>
> 文档解析 → 分块 → Embedding → 向量存储 → 用户问题向量化 → Top-K 召回 → Rerank → 拼接上下文 → LLM 生成。
>
> 1. RAG 效果不好怎么排查？
>
> 先区分检索问题还是生成问题。
>
> 检索问题可以分析 Chunk 大小、Embedding 模型、召回策略和重排序。
>
> 如果已经召回正确内容，模型仍然回答错误，则需要进一步检查 Prompt、上下文组织和模型能力。
>
> 1. 了解 BM25 和混合检索吗？
>
> 简单讨论了 BM25、向量检索与融合排序。
>
> 这部分只做过基础 Demo，没有深入实践，如实说明了技术边界。
>
> # ============================================================ 七、Coding Agent、MCP、Harness
>
> 1. MCP 是什么？CLI 是什么？
>
> MCP 是 AI 应用连接外部工具和数据源的标准化协议，方便工具能力复用。
>
> CLI 是命令行交互界面，两者不属于同一层面的概念。
>
> 1. 了解子 Agent 吗？什么场景需要？
>
> 讨论了主 Agent 负责整体规划、子 Agent 负责专项任务或信息收集的协作方式。
>
> 重点在于任务拆分、并行执行和上下文隔离。
>
> 1. 什么是 Agent Harness？
>
> 主要理解为围绕模型构建的执行环境和工程机制，包括工具、上下文管理、权限控制、状态管理等。
>
> 分享了自己对 Claude Code 和 Pi Agent 的使用体验。
>
> Claude Code 更强调完整的开箱即用能力，Pi Agent 则采用比较极简的核心设计，通过插件和扩展实现更多功能。
>
> 讨论了模型能力、Harness 复杂度、Token 成本和可扩展性之间的取舍。
>
> 1. 平时如何使用 AI Coding 完成开发？
>
> 简单需求：明确需求和约束，让 AI 完成实现，再进行审查和测试。
>
> 复杂需求：先对齐需求、分析历史代码和上下文，按照软件工程思想拆解任务，分阶段执行和验证。
>
> 强调了 Context Engineering 和开发过程中的质量控制。
>
> # ============================================================ 八、岗位相关场景题：企业内部 AI Coding 平台
>
> 1. 假设要做一个面向穿戴产品研发的 AI 应用开发平台，你现有的网页生成 Agent 能复用什么？
>
> 这是后半段最贴合岗位实际工作的一道题。
>
> 需要注意，这里讨论的不是给普通用户开发一个儿童手表 AI 助手，而是如何通过企业内部 AI Coding 平台辅助研发人员开发穿戴设备相关的软件应用。
>
> 我主要从平台能力复用和差异化改造两个方面回答。
>
> 【可以复用的部分】（1）Agent 工作流编排。（2）需求分析和 Prompt 增强。（3）Tool Calling 和工具管理机制。（4）代码生成与质量检查流程。（5）流式执行状态展示。
>
> 【需要重新适配的部分】（1）穿戴应用对应的工程结构与技术栈。（2）专用代码生成工具和开发规范。（3）构建、运行、测试和部署工具链。（4）穿戴应用的交互约束与质量验证。（5）更系统化的 Agent 评测体系。
>
> 我认为核心价值不在于直接复用网页生成代码，而是将底层 Agent 编排和工具调用能力迁移到新的研发场景。
>
> # ============================================================ 九、个人复盘与建议
>
> 这场面试与传统 Java 后端面试区别很大。
>
> 虽然我的实习经历主要是 Java 后端，但这次面试基本没有围绕 Java 集合、Spring、MySQL、Redis 等传统八股展开。
>
> 面试官更关注：
>
> （1）Coding Agent 的真实实现：模型如何调用工具，工作流如何设计，执行失败怎么处理。（2）上下文工程：AI 如何理解现有项目，如何管理历史约束，避免修改破坏原有业务。（3）Agent 可靠性：如何控制危险操作、限制重试、管理 Token 成本。（4）自动化评测：如何证明 Agent 真正完成了开发任务，而不只是输出了代码。（5）平台化能力：如何把个人 Demo 中的 Agent 能力沉淀为企业内部可复用的 AI Coding 平台。
>
> 如果准备这个岗位，我建议把重点放在 Coding Agent、MCP、CLI、Skill、Harness、Context Engineering、工具安全和 Agent 评测上，而不是单纯刷 Java 后端八股。
>
> 另外，面试官会深挖真实项目的技术边界，例如质检究竟做到了什么、多轮修改如何保证代码不被覆盖，以及为什么选择单 Agent 而不是多 Agent。
>
> 整体是比较深入的项目交流，个人感觉面试官更看重工程实践和技术判断，而不是单纯记忆概念。
>
> 面试官表示预计 1～3 个工作日内反馈结果。
>
> 以上是本次面试复盘，希望能帮到准备 AI 应用开发、Coding Agent 和 AI 研发工具平台相关岗位的同学。
>
> 祝大家秋招顺利！
