> 在面栈阅读：[主 Agent 与子 Agent 的职责如何划分？](https://mianstack.com/question/q-3748)

## 核心回答

主 Agent 负责**全局目标、任务依赖、结果汇总和最终交付**；子 Agent 负责完成范围明确、可以单独验收的子目标，并把结果及依据交回主 Agent。划分依据是任务、上下文、工具和权限的边界。

例如技术调研中，主 Agent 明确要比较的维度并拆分工作；文档子 Agent 核对官方接口，实验子 Agent 执行给定实验，各自保存局部过程，最后返回发现、证据和缺口。主 Agent 检查口径与冲突，决定补查还是形成结论。工具执行、并发限制、权限和预算由运行时落实，不能只靠角色提示词约束。

若一个步骤只需输入参数并确定性地返回结果，如 `PDF` 转换，通常作为工具即可；需要在局部目标内自主选工具、根据反馈继续行动时，才适合独立子 Agent。

## 怎样把边界落到可执行任务？

### 主 Agent 保持全局一致性

它需要知道用户真正要交付什么、有哪些已确认约束、哪些子问题互相依赖，以及什么时候信息足够。它负责维护任务清单和整体预算，避免几个子 Agent 重复解决同一问题，也避免每个角色只完成局部工作而没人负责最终答案。

主 Agent 可以根据新发现调整分工，但权限扩大、资源范围和业务状态变化应经过运行时策略校验。子 Agent 返回“需要另一个工具或补充输入”时，由主 Agent 决定后续安排，而不是让角色无边界地互相转交。

### 子 Agent 获得一个完整但有限的任务契约

派发时应交代：目标与范围、必要输入、可用工具、依赖、完成标准、返回格式和剩余预算。例如“核对这两个SDK版本的批处理接口，给官方链接和差异”，比“你负责查资料”清楚得多。

子 Agent 在自己的上下文中探索、记录工具结果，返回结构化摘要和产物引用。任务ID、状态、结论、证据位置、缺失项、适用版本应能对应起来；原始材料较大时按引用读取，不必全部复制进主上下文。摘要应保留核查入口，不能压缩成无法溯源的一句结论。

### 运行时管理执行边界

| 边界     | 具体做法                                                     |
| -------- | ------------------------------------------------------------ |
| 状态写入 | 子任务写自己的结果槽，主 Agent 或汇总节点写最终结果          |
| 并发     | 输入齐备且互不依赖才并行；限制并发数和共享资源               |
| 权限     | 工具与数据源校验身份和访问范围；提示词不承担鉴权             |
| 预算     | 子任务获得根任务预算的一部分，重试和派生继续计入总量         |
| 失败     | 明确哪些结果必需，哪些可以降级；等待、失败与部分完成分别返回 |

这样主 Agent 负责决策与验收，运行时负责执行约束，子 Agent 专注局部任务，不会把所有职责都集中到模型的一次自然语言判断中。

## 为什么要把检索抽成子 Agent？

若检索过程需要多次改写查询、读取不同材料并评估证据，独立上下文可以把大量搜索过程留在子任务里，主 Agent接收高密度的结论和来源。同时可以只给它检索工具，缩小执行范围。

代价是多一次任务交接、模型调用和摘要，关键细节也可能在压缩时丢失。仅需一次固定检索时，直接在主 Agent中调用工具更简单。是否拆分，应看任务成功率、引用正确性、延迟和费用，而不是只看角色数量。

## 常见追问

**主 Agent必须汇总所有回答吗？**

在主子任务模式中，主 Agent通常统一交付。若产品需要用户转到某个专家继续对话，可以采用 `Handoff`，把控制权和必要上下文交给专家；它与子 Agent执行后返回主管的模式不同。

**子 Agent用同一模型，还算独立吗？**

可以。独立性来自目标、上下文、工具和运行状态边界，不要求不同模型或独立进程。同样，连续调用两个不同模型也不自动构成多 Agent。

**结论冲突由主 Agent投票吗？**

应先核对来源、版本、时间和适用范围。计划值与实际值、旧接口与新接口可能都正确，只是条件不同。确实冲突时补查证据；证据仍不足就保留分歧，多个子 Agent重复同一来源不能算多份独立佐证。
