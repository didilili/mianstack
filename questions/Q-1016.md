> 在面栈阅读：[如何理解 LangChain 的底层原理？](https://mianstack.com/question/q-1016)

## 核心回答

`LangChain` 的底层思路是**把模型应用中的数据和调用统一成协议，再把组件组合成执行流程**。模型接入不是直接散落在业务代码中的 `HTTP` 请求，而是经适配器转成统一的消息、工具调用和响应对象。

可以分三层理解：

1. **组件与适配**：`Message` 表达用户、模型和工具的消息，模型接口屏蔽厂商请求差异，`Tool` 描述名称、参数结构和执行入口，检索器返回带元数据的文档。
2. **调用组合**：`Runnable` 提供 `invoke`、`ainvoke`、`batch`、`stream` 等入口；`LCEL` 把遵循这些协议的组件组合成顺序、分支或并行流程。例如 `Prompt` 生成模型输入，模型返回消息，解析器转换为业务结果。
3. **Agent 运行**：在 v1 路线中，`create_agent` 基于 `LangGraph` 组织模型与工具节点。模型提出工具调用，程序执行并把结果写回状态，再调用模型，直到结束。状态、检查点和中断恢复由运行时承接，业务规则通过工具、节点和中间件接入。

所以，`LangChain` 既有可独立使用的类库组件，也有高层 Agent 入口；它并不是“上传文档就自动得到知识库”的托管平台。

## 展开说明

### 一条链为什么能够组合？

关键是相邻组件的输入输出契约能接上。`prompt | model | parser` 中，`Prompt` 接收变量字典并产生提示对象，聊天模型读取消息并产生 `AIMessage`，解析器再提取文本或结构化结果。管道符会构造组合对象，运行时再按顺序调用各步；它不是在定义链时立刻发送模型请求。

组合后的整体仍然遵循 `Runnable` 接口，因此可以继续嵌入另一条流程。并行组合让同一输入交给多条分支，再按键汇总结果；是否真正异步、能否逐块透传，还取决于组件实现及调用方式，不能把所有 `stream()` 都理解成每一步逐 Token 输出。

### Agent 为什么不能只理解成普通 Chain？

固定链的处理结构由代码提前确定，Agent 的下一次动作还取决于模型和工具反馈。例如问题是“查询两地天气后给出行建议”：

- 模型收到用户消息和工具定义，产生带 `tool_calls` 的模型消息。
- 执行器用工具名找到实现，校验参数并执行。
- 每个结果通过 `tool_call_id` 与对应请求关联，形成 `ToolMessage`。
- 消息进入 `State`，模型读取实际天气，再决定补查或给建议。

这些步骤由图中的节点、路由和状态更新驱动。`Middleware` 可以在模型调用或工具调用周围裁剪上下文、处理错误或拦截动作；可信身份和资源权限仍由应用传入并校验。

### State、Context、Store 分别放什么？

`State` 保存这条执行线程中会变化的数据，例如消息、当前计划和中间结果。运行上下文提供本次调用的用户身份、配置、依赖等信息，避免让模型自己生成可信身份。`Store` 用于应用定义的跨线程数据，例如用户偏好或长期事实。检查点则保存图执行状态，支持继续同一线程。

它们可以协作，但职责不同。设置了 `thread_id` 仍需配置检查点后端；内存后端只能在相应进程存活期间保存状态。旧版 `Chain`、`AgentExecutor` 和 v1 `create_agent` 的入口及执行结构也应分别讲清。

## 常见追问

**为什么不直接用厂商 SDK？**

单次调用、供应商固定时直接用 SDK 很合适。多模型适配、工具协议、流式事件和追踪开始重复出现时，统一组件能降低业务与厂商格式的耦合。代价是多一层抽象和版本维护，仍需理解请求、响应与底层执行。

**它会自动完成 `RAG` 吗？**

它提供文档加载、切分、`Embedding`、向量存储和 `Retriever` 等组件。开发者需要组织离线入库和在线检索链路，确定更新、过滤与引用规则；并非安装框架就已经建立可用知识库。
