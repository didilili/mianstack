> 在面栈阅读：[项目中遇到过哪些模型幻觉，如何分析原因并处理？](https://mianstack.com/question/q-7905)

## 核心回答

下面以**产业情报研读平台**给出项目排障答法示例：采用 `Python`、`FastAPI` 与 `DeepAgents/LangGraph`，主Agent组织网络、数据库和知识库助手，最后生成研究报告；产业证据与结论关联属于行业适配设计。

一个典型问题是资料只证明“发布样机、计划交付”，报告却写成“已规模量产并交付”。我会先把这句话与当时的原文、实际模型输入和工具返回对照，再沿资料获取、检索、上下文、子Agent汇总到最终生成逐段找出第一处扩大事实的位置。没有证据进入输入，就先修来源链；证据充分却仍然扩大结论，再调整生成和核验。

处理上让来源返回带位置、时间和主体的证据，区分计划、样机、交付等状态，最终结论逐条关联支持材料。信息不足保留缺口；修复后用同一批资料回放，检查同类错误与正常回答是否一起改善。

## 先固定可回放的错误现场

保留用户问题、研究截止日期、材料快照、各助手输入输出、主Agent实际输入和最终报告，记录模型、提示和工具版本。仅凭最终一句错误，不能判断是模型凭空补造，还是上游先给了错误摘要。

把错误声明拆开，例如“产品A已经量产”和“产品A已经交付”是两件事。核对同名企业、产品别名、材料发布时间与事实发生时间，并区分原始公告和多处转载，避免转载数量被误当作独立佐证。

## 沿链路怎样定位？

| 观察到的情况                               | 更可能的原因与后续动作                         |
| ------------------------------------------ | ---------------------------------------------- |
| 原始资料就没有交付证据                     | 补查来源或保留未知，不能要求模型靠措辞完成事实 |
| 正确原文存在，但未进入返回结果             | 查检索、过滤、解析和工具输出契约               |
| 助手结果正确，汇总摘要丢掉“计划”           | 查子任务提示、摘要与交接过程                   |
| 主模型输入保留了“尚未交付”，最终写成已交付 | 查生成是否越过证据或忽略否定条件               |
| 引用链接真实，却只支持样机发布             | 查结论与引用的支持关系，而不只检查链接可打开   |

可以做受控对照：固定问题与生成配置，先提供人工核对过的充分证据，再与真实检索输入比较。如果充分证据下表现改善，说明上游缺口值得优先查；若仍答错，则继续检查指令与生成。这个实验给出归因线索，不能一次运行就证明唯一根因。

## 对这个项目，哪些改动最具体？

现有实现中，主Agent确实会按需委派网络、数据库和知识库助手；但 `create_ask_delete()` 从 `RAGFlow` 流式响应里取出并拼接的是 `answer` 文本，没有把结构化原文片段、位置和来源一并交给主Agent。因此，主Agent拿到的可能已经是另一层生成文本，不能当作可直接核验的原始证据。

行业适配可以扩展来源输出：至少带来源标识、URL或文件位置、发布日期、事实时间、企业/产品、关键原文和状态；如果现有接口无法提供原文，就改接可核对的检索片段，或明确只返回待核查线索。

再建立“证据—声明—报告段落”的关联。资料写计划，就只支持计划；样机发布不自动支持量产，量产也不自动证明已交付。冲突材料保留各自时间与出处，需要补查时让相关来源助手继续查，而不是通过多Agent投票决定事实。

生成提示要求结论受证据支持，并在不足时说明缺口；程序校验来源ID、日期字段和引用是否存在，语义支持关系再做证据对照或人工抽样。独立模型可以辅助筛查，但不把它的认可当作事实证书。

## 怎样验证没有“改好这一例，改坏其他例”？

固定资料准备样机发布、计划交付、已交付、同名实体、多处转载、材料冲突和确实缺证据的样本。分别测证据是否进入输入、关键声明是否受支持、时间与状态是否准确，以及正常可回答任务有没有被过度拒答。

用新旧方案处理相同问题，保留逐样本变化、调用次数、耗时和费用；错误分层到来源、交接与生成，不只汇总一个总分。这里的处理与验收是可执行设计，实际收益仍需接入后的回放结果；不能把报告文件成功导出当成事实核验成功。
