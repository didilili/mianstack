> 在面栈阅读：[是否亲自部署过大模型？](https://mianstack.com/question/q-1267)

## 核心回答

可以先分清自己做到哪一层：调用云 API 是使用推理服务；把权重加载到本机运行是本地推理；把模型接成其他程序可调用、能观察和维护的接口，才进一步涉及服务化部署。

下面是一段假设部署经历，采用 `Qwen3-0.6B` 关键词模型与 `vLLM` 路线说明具体工作：

“我负责把关键词抽取模型接成推理服务。先准备完整权重、分词器和对话模板，核对 GPU、驱动与依赖，再在独立环境中启动 `vLLM`，配置服务模型名、精度、上下文和并发预算。之后检查模型列表，再发真实关键词请求，核对返回内容和格式；接到文章管理程序后，用不同长度和并发的输入测试错误率、响应时间与显存，并保留配置、日志和测试结果。部署成功既要看服务能启动，也要看业务请求是否达到要求。”

## 展开说明

### 模型文件与环境怎样准备？

固定基础模型与权重修订，检查配置、分词器、权重分片和索引是否齐全。若使用 `LoRA`，要确定是“基础模型加 Adapter”还是已合并完整模型，不能把只有 Adapter 的目录当成完整权重。

教程的冻结示例是 `V100-32GB`、`vLLM 0.9.2`、`Transformers 4.53.3` 与 `FP16`，训练和推理使用独立环境。它说明的是这一组环境的兼容路线，不是部署该模型的最低显存，也不是当前版本推荐配置。换硬件或引擎版本，要重新核对计算能力、精度、驱动及二进制依赖。

### 启动参数怎样解释？

模型路径决定实际加载文件，服务别名决定请求中的模型字段；分词器与对话模板决定角色消息怎样转换成模型输入。`--max-model-len` 控制输入与输出合计的上下文上限，不能把全部额度都分配给输入；`--max-num-seqs` 约束调度中的并发序列数，显存预算还受权重、缓存和运行开销影响。

显存不足时，先看是哪一阶段失败。权重加载放不下，与长上下文或并发造成缓存压力，处理办法不同。缩短上下文、降低并发或使用合适量化，都需要重新验证质量与性能；不是把显存比例参数调小就一定能运行。

### 验收怎样从连通走到可用？

先查服务状态和 `/v1/models`，确认实际模型名；再调用 `/v1/chat/completions` 检查模型是否真正生成。关键词任务还要核对分号、无关前缀、主题覆盖及异常输入，不能只看 HTTP 成功。

对同一组输入，记录长度、并发、输出预算、版本和生成设置，观察首字延迟、总耗时、吞吐、错误率与显存。并发更高但排队更久，不一定符合用户目标。没有压测结果时，部署说明保留验证方法，不给无依据的吞吐数字。

服务接入时再明确监听范围、调用方认证、超时、日志与重启方式。教学中只监听回环地址并通过隧道访问，是一种连通性路线；生产还需按实际网络与权限要求设计入口。停止隧道和停止模型服务是两件事。

## 可能的追问

### 服务起来了，但回答乱码或不按格式，先查什么？

先核模型与分词器是否匹配、模板和停止条件、实际生成参数及思考模式。模板错了会改变输入，不要一开始就归因于模型能力或微调失败。

### 在笔记本上跑过模型，算部署吗？

可以说明是本地推理或本地服务化实践，再展开实际完成的加载、运行和接口工作。是否达到持续服务要求，要看调用、并发、恢复和运维验证，不能仅凭“能回答一句话”判断。
