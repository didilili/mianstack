> 在面栈阅读：[如何为 Skill 构建回归评测集？](https://mianstack.com/question/q-3883)

## 核心回答

Skill 的回归评测集应从**实际任务、历史失败和技能边界**构建。每条样本不仅有一句输入，还要固定必要的文件、历史、工具、权限与业务状态，并写明应选什么技能、最终产物应满足什么条件。

样本至少覆盖正常任务、隐含触发、相近但不适用、输入缺失、工具故障和历史回归。新旧版本在相同环境与预算下运行，分别比较选用是否正确、任务结果是否正确，以及成本和副作用。发现新失败后，确认原因并加入对应分层；保留独立留出集，避免为了通过旧样本而失去泛化。

## 一条样本里需要保存什么？

| 信息                           | 作用                                   |
| ------------------------------ | -------------------------------------- |
| 样本 ID、场景、来源与标签      | 追踪真实问题与所属能力                 |
| 用户输入和必要历史             | 包括隐含意图、已有确认和本轮更正       |
| 文件/数据快照与起始状态        | 保证各版本面对同一个问题               |
| 可用技能、工具、权限与故障配置 | 区分路由、执行和依赖问题               |
| 预期行为与可接受结果           | 可补问、可拒绝、可成功，不要求唯一措辞 |
| 评分器与关键断言               | 检查产物、业务状态和必要过程约束       |
| 模型、Skill、工具与评测集版本  | 支持复现与回归定位                     |

比如报表 Skill 的样本可以是“统计十月份销售额，退款按发生月份归属”。给定跨月退款数据，断言金额、统计范围和报告文件内容；它比“回复中出现销售额三个字”更能验证能力。

## 样本从哪里来，怎样扩展？

第一批来自用户任务、手工验收案例、已确认的投诉与修复记录。新能力尚未有日志时，根据业务规则构造种子，但生成模型提供的输入和答案需要核对，不能直接当真值。

围绕一个确定任务改变关键条件：

- 同义表达或隐含请求：不直接点名技能，检查是否仍能选对。
- 相邻任务反例：例如“解释报表字段含义”不一定需要启动完整报告工作流。
- 缺失与冲突：缺少日期、同名字段口径冲突、用户中途改月份。
- 依赖与状态：工具超时、返回空表、已有同名文件、失败后重试。
- 组合与长程：分析后生成报告，多技能交接，长历史中保留关键约束。

同一原始事件的改写、相同文件的变体应按组划分开发集和留出集，避免几乎相同的样本同时出现在两边。常见任务用于观察总体表现，低频但重要的失败单独设门槛，不能被平均分淹没。

## 怎样打分和比较？

**触发层**检查该用时是否选中、不该用时是否误触发，以及多技能是否缺失或冗余。显式指定技能与自动匹配分开评估。

**结果层**优先用程序检查可确定的内容：文件存在且可解析、金额与参考计算一致、字段齐全、未越权修改。允许等价实现，除非某个步骤本身就是业务要求，不强行要求调用顺序和内部实现逐字一致。

**语义层**检查结论是否受数据支持、缺口是否说明清楚，模型裁判可以辅助，但需要和人工标注校准；出现分歧时回看原始轨迹。

对新旧版本使用同一批样本与初始快照，隔离临时文件、缓存和外部状态。关键随机任务进行多次试验，保存逐样本改善、退步和不变情况；同时记录 token、调用次数和端到端时延。总体分数上升时，仍要检查重要场景是否退步。

## 回归集怎样长期维护？

保留稳定的核心集跟踪历史能力，再维护新增难例集暴露新缺陷。每次修复加入最小失败样本和必要变体；业务规则变更时同时版本化样本、预期结果与旧基线，而不是直接改答案后宣称通过。

评测失败先区分技能问题、依赖波动和评分器错误。不能因为一个合法输出与参考措辞不同就判错，也不能为了提高通过率删除真实的困难样本。样本量由覆盖面、风险和希望检出的差异决定，没有适用于所有 Skill 的固定条数。
