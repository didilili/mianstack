## 核心回答

主要差异是**哪些能力由团队控制，哪些通用工程责任由谁维护**，不能只用“自研更灵活、开源更方便”概括。

开源框架提供模型和工具接入、编排、状态或协作等能力，可以减少重复实现；代价是理解其抽象、适配业务和跟进版本。自建可以直接围绕内部工具、权限、任务状态和观测设计接口，但相应的异常、恢复、兼容和维护也要自己负责。

首先还要分清“自建”的范围：内部 SDK 可能只是对开源底座的业务封装，也可能替换部分运行机制，或者完全自写循环。常见方案是复用成熟组件，再自建业务策略和适配层；是否值得替换底层，要用明确的能力缺口和同条件验证决定。

## 展开说明

### 1. 先把框架拆成职责，才能比较

可以按模型适配、工具注册执行、任务编排、上下文、状态持久化、权限和追踪分别说明。内部 SDK 若只增加统一身份注入、工具目录和日志格式，底层仍使用开源状态图，就应讲清“复用了哪些机制、自己增加了哪些能力”。

以 LangGraph 为例，它提供状态、节点、边及检查点等低层编排能力，业务仍需要定义状态字段、工具权限、成功条件和外部副作用处理。它能支持暂停恢复，不意味着仅安装依赖就已经具备持久数据库和完整业务授权。

反过来，一个封装了统一业务工具与接口的内部 SDK，也不必实现自己的图引擎才能有价值。重点是它解决了什么重复问题，以及底层依赖是否清楚。

### 2. 开发、控制与维护成本怎样比较？

开源方案能复用生态集成和已有执行机制，但要理解消息、状态更新、错误和回调语义；框架抽象不匹配时，可能产生适配代码或难排查的行为。升级还要验证接口、序列化状态和插件兼容。

自建初期可以更贴近少量业务，但需求增加后，需要持续处理并发状态、超时取消、失败重试、检查点、版本迁移和可观测性。代码由自己维护有利于修改，却不自动意味着更可靠或更便宜。

性能也应拆开测。模型和外部工具耗时、重复调用、上下文大小、持久化策略都可能主导延迟。只有相同任务、模型、工具、恢复保证和并发条件下的比较，才能说明某层封装是否值得优化，不能凭类和依赖少就断言自研快。

### 3. 一个实际可执行的选择过程

先列出当前必须支持的流程和约束，例如多步检索、指定业务权限、中途暂停和跨进程恢复。用代表性任务验证开源方案，并标出可通过配置、适配层或扩展点满足的部分。

若核心循环和状态能力合适，就在上层封装统一的任务、工具、身份和追踪接口，避免业务到处依赖底层实现细节。若某个抽象持续阻碍业务，先考虑局部替换；只有确实需要不同的运行模型且团队能长期维护时，再扩大自研范围。

验证不只看正常完成，还看工具失败、取消、状态恢复、版本升级，以及任务成功质量、延迟、费用和排障成本。迁移时先保留旧方案作为对照，确认关键路径与恢复语义一致，再逐步替换。

## 常见追问

### 自建框架与 AutoGen、CrewAI 有没有本质区别？

先对照实际使用的版本和职责：是否依赖模型动态分工，任务和共享状态怎样组织，工具如何注册，异常与恢复由谁处理。如果主要能力相近，差异可能在业务集成、执行控制和内部部署要求；不能只因内部类名不同，就认为发明了另一种 Agent 原理。

### 内部 SDK 和开源框架是同一个东西吗？

可能存在依赖关系，但要看代码边界。可以说“开源框架负责图调度和检查点，内部 SDK 负责企业工具、权限及日志约定”，也可能部分组件完全自研。用真实调用链和模块说明，比笼统回答“都是自研”更清楚。

### 不用框架是不是就没有依赖风险？

仍有模型 API、数据库、HTTP 客户端和工具服务等依赖，也有自建实现本身的缺陷与维护风险。只是改变了依赖与责任分布；应看版本锁定、兼容验证、可替换边界和团队维护能力。
