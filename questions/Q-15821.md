> 在面栈阅读：[项目中的 Prompt 如何编写和组织？](https://mianstack.com/question/q-15821)

## 核心回答

下面以**门店经营分析助手**给出项目答法示例：基于电商问数的 `Python`、`LangGraph` 链路，将经营问题转换为 `SQL`；门店净销售额、退款归属和访问范围属于行业适配设计。

我会按节点分别组织 Prompt：关键词抽取负责理解问题，候选过滤负责缩小可用表和指标，`SQL` 生成负责把问题与元数据变成候选 `SQL`，纠错 Prompt 负责结合数据库错误做必要修正。稳定的任务规则保存在模板，运行时填入表字段、指标口径、日期、数据库环境和当前问题；业务节点负责组装输入、调用模型并处理输出。

重点是让每段 Prompt 对应一个明确职责与输出，再用固定经营问题检查口径、时间和结果。比如“十月净销售额”要明确采用本期实收减本期实际退款，不能只告诉模型“算销售额”。

## 现有模板怎样加载与装配？

电商问数将提示词放在 `prompts/*.prompt`，项目自己的 `load_prompt(name)` 按名称读取文本。`SQL` 生成节点用 `PromptTemplate` 声明五个变量：

| 变量           | 输入来源与用途                       |
| -------------- | ------------------------------------ |
| `table_infos`  | 前置检索和合并后的表、字段与关联信息 |
| `metric_infos` | 指标定义、计算与过滤口径             |
| `date_info`    | 当前时间及日期相关背景               |
| `db_info`      | 数据库类型和版本                     |
| `query`        | 本轮用户经营问题                     |

节点将结构化上下文序列化成 `YAML`，填充模板后调用模型，使用 `StrOutputParser` 取出纯文本 `SQL`，写回状态中的 `sql`。`StrOutputParser` 只是取得文本，不会证明 `SQL` 的业务正确性。

这条实现使用文本模板，不是已经拆分好的 system/user 消息模板。需要多角色组织时可以改用 `ChatPromptTemplate`，但应同步检查角色、历史和工具结果如何进入请求，不能只换类名。

## 具体提示应该包含哪些业务规则？

`SQL` 生成模板已经包含仅使用给定表字段、遵循相关指标定义、只生成查询语句、符合数据库方言，以及只输出一条纯 `SQL` 等要求。纠错模板在这些上下文之外增加原 `SQL` 与 `error`，强调保持业务语义并做最小必要修正。

门店场景可以在现有机制上补充如下业务要求，属于适配设计：

```text
任务：根据给定表结构和指标定义生成一条查询SQL。
净销售额：本期实收减本期实际退款，退款按发生时间归属。
只使用提供的表字段，不把订单发生月份当成退款发生月份。
指标含义或必要字段缺失时，返回待澄清原因，由流程进入补问分支。
仅在输入充分时输出候选SQL；数据库方言按db_info。
```

这里的“待澄清原因”需要应用层支持对应分支或结构化输出，不能直接加入现有只接受纯 `SQL` 的节点后就送往执行。现有模板在指标未覆盖时允许根据语义与通用业务常识生成，这与严格经营口径有差距；业务上更稳的改法是先识别缺口，再补问或补充已确认指标。

## 模板怎样维护与验证？

固定规则、变量名与输出契约一起版本化。模板更新时记录修改原因、失败输入、模型与上下文快照，回放正常指标、跨月退款、部分退款、同比日期、缺字段和越界查询等用例。

对于净销售额，不只比较 `SQL` 字符串，而是对照人工确认的口径、查询结果和数据范围。等价 `SQL` 可以产生同样正确的结果；能执行但把退款归错月份，仍然是业务失败。

权限、只读连接和查询范围由执行层落实。现有图中纠错节点直接进入执行，纠错结果不会再次经过原校验节点；增加复验、有限重试与失败出口是可以安排的工程改进，不能靠“只生成安全 `SQL`”一句提示替代。

## 个人职责怎样讲具体？

若承担的是 Prompt 与上下文适配，可以围绕“输入—处理—输出”说明：接收指标定义、别名和前置召回结果，整理字段依赖、日期与口径，传给生成/纠错模板，输出候选 `SQL` 和可检查状态；再用业务问题定位哪项条件首次丢失。这样能够解释模板、程序与验证的分工，而不只是说“写了几段提示词”。
