## 核心回答

从本地到云端，我会把**可复现的交付产物、云上运行环境、配置与数据、发布切换、验证与回退**这条链路讲清楚。以下以带网页和 Python API 的 Agent 应用为例：

1. **固定交付版本**：锁定代码和依赖，完成相关测试，将前端构建产物、后端镜像与版本信息保存下来，避免服务器临时安装出另一套环境。
2. **准备运行环境**：根据并发、存储和模型调用方式选择云主机或托管服务，配置网络、域名和 HTTPS，明确前端、API、数据库、缓存及检索服务分别部署在哪里。
3. **分离配置与数据**：数据库地址、模型端点等按环境注入；密钥留在服务端；会话、文件和业务数据使用合适的持久存储，需要迁移时提前备份并验证恢复。
4. **部署并逐步切换**：在测试环境用同一交付版本验证，生产按需要采用维护窗口、滚动、蓝绿或灰度发布，同时处理新旧版本兼容与存量任务。
5. **验证后持续观察**：从真实入口完成关键业务链路，检查错误率、延迟、资源和模型费用；异常时停止扩大流量，按预案切回旧版本，并核对数据状态。

上线成功应当是用户能稳定完成目标任务。容器显示运行、首页能打开，只能证明其中一部分。

## 先说明云上每个组件负责什么

一种适合小规模应用的方案是：前端静态文件由 Web 服务或静态托管提供，HTTPS 入口把 API 请求转发给后端；后端调用模型、工具、数据库和检索服务。数据库、文件及会话存储按实际需要独立保存，日志进入可查询的位置。

如果主要调用外部模型 API，应用服务器通常不需要因为“使用大模型”就配置 GPU；自托管模型时，才需要另外评估显存、模型加载、推理吞吐和模型服务的部署。远端模型与工具接口是否可达、额度是否充足，也属于上线依赖。

单机与 Compose 可以作为简单起点；已有容器平台或多实例运维需求时，再使用相应的编排能力。不是所有项目上线都需要 Kubernetes、多机房或复杂微服务。

## 从本地搬过去的，不只是代码

**产物方面**，记录提交版本、依赖锁文件和镜像摘要，测试与生产使用同一份已构建产物。还要确认目标机器的操作系统与 CPU 架构能够运行该镜像。重新构建同名镜像、手动改容器文件，都会增加版本追溯的难度。

**配置方面**，区分浏览器访问的公开地址与容器之间的内部地址。本机的 `localhost`、Windows 路径或开发端口，不能直接作为云上的依赖配置。HTTPS、反向代理、允许的来源和应用基础路径也要一起检查；模型密钥、数据库凭据由服务端读取，不放进前端构建产物。

**数据方面**，镜像提供运行环境，不包含运行中的数据库状态。数据库、向量索引、上传文件等应明确落到数据卷、对象存储或外部服务；迁移时分别处理镜像、配置和数据。挂了数据卷也不等于已经有备份，备份应确认能够恢复，不能只检查“文件存在”。

多实例后还要检查共享状态。进程内字典或内存检查点只对相应进程有效，换一个实例就可能读不到会话；需要跨实例延续时，应使用合适的外部状态存储。长任务还需考虑实例退出后由谁继续处理，不能只把 API 副本数调大。

## 发布方式取决于能否中断和能否兼容

小型应用能接受短暂停机时，可以安排维护窗口更新，再完成启动和业务验证。需要持续服务时，可以保留旧实例，先启动新版本，确认能接收业务请求后再切换；灰度则先让一部分用户或流量使用新版本，观察后逐步扩大。

普通的 Compose 服务重建并不自动等于无中断滚动发布。是否持续可用，要看是否保留可用实例、入口怎样分流，以及旧实例何时停止接收新任务。退出前还要处理进行中的请求、流式连接和后台任务，避免直接终止造成结果丢失或操作被重复执行。

如果涉及数据库迁移，先判断新旧应用能否同时使用变更后的结构。迁移任务应受控执行，避免每个副本启动时争抢修改数据库。需要兼容发布时，可以先增加兼容字段、发布新代码，确认旧版本退出后再做清理，而不是一次删除旧代码仍依赖的字段。

回退也要分别考虑应用和数据。切回旧镜像可以恢复代码版本，却不会自动撤销新版本写入的数据或不可逆迁移；因此发布前要保留旧产物与配置，并明确哪些变化可以直接回退，哪些需要数据修复或继续向前处理。

## 验证要穿过真实入口和实际依赖

先检查服务启动、进程托管和异常重启，再从公开域名完成登录、一次正常提问、工具或检索调用、结果返回和会话延续。流式回答要经过实际反向代理验证，不能只在开发接口里看到了流就算通过。

同时检查必要的异常路径：模型接口超时、数据库不可用、检索无结果时，系统能否给出合理反馈，是否会无界重试。健康检查应有明确含义，既要确认进程在运行，也要判断当前实例是否具备接收请求的条件；自动重启不能替代故障定位。

运行记录用请求标识串起 API、模型和工具，便于区分网络问题、检索失败和业务执行失败。观察成功率、端到端延迟、错误与超时、CPU/内存、数据库连接、队列积压及每个任务的模型费用。发布后将这些指标与旧版本比较，发现异常再定位对应版本、配置和依赖变化。

## 常见追问

**本地能运行，云上却访问不了，先查哪里？** 沿访问链路逐段检查：域名解析和 HTTPS、入口监听与转发、云网络和防火墙、应用监听地址与端口、容器网络、依赖连接及日志。先确认请求在哪一段失败，再调整对应配置。

**为什么不是 SSH 上去启动程序就结束？** 手动启动可以用于诊断，但正式运行还需要处理退出登录、服务器重启、进程崩溃、配置变更和日志保留。可以由 systemd、容器运行时或云平台承担托管，选择与项目规模相称的方式。
