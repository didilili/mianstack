> 在面栈阅读：[常见的向量索引算法有哪些，如何选择？](https://mianstack.com/question/q-3727)

## 核心回答

常见方案可以按**精确扫描、聚类分桶、近邻图和向量压缩**来理解：`Flat`逐个计算距离，适合作为精确基线；`IVF`把向量分桶，查询时只搜索部分桶；`HNSW`通过分层近邻图减少距离计算；`PQ`把向量编码成较短的码，降低存储与计算成本，但会引入量化误差。`PQ`还可以和`IVF`等结构组合，因此这些名称并不全是互斥选项。

选型要在相同数据、距离度量和过滤条件下，对比达到目标召回率时的延迟、内存、构建和更新成本。小数据或少量查询可先用`Flat`；追求低延迟、内存较充裕时评估`HNSW`；数据规模和内存压力较大时，再比较`IVF`及压缩方案。例如企业知识库还要带部门权限过滤，就应使用真实过滤条件测试，不能只依据“有多少条向量”选索引。

## 这些方案分别省了什么？

| 方案            | 主要思路                                                         | 主要代价与适用判断                                                               |
| --------------- | ---------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `Flat`          | 对候选范围内的全部向量计算距离，再取`Top-K`                      | 不因候选裁剪或量化而漏掉近邻；计算量随数据量增长，适合基线、小集合或查询少的场景 |
| `IVF_FLAT`      | 训练聚类中心，将向量放入倒排桶；只扫描选中的桶，桶内使用原始向量 | 少扫桶换速度，也可能漏掉未探查桶中的近邻；需要训练，仍要保存原始向量             |
| `HNSW`          | 上层稀疏图快速导航，底层扩大候选搜索                             | 用图连接存储和构建成本换低延迟；查询探索范围影响召回，维护与过滤表现依实现而异   |
| `PQ` / `IVF_PQ` | 将向量拆成子向量，用码本编号近似表示；可叠加分桶检索             | 减少向量存储和距离计算，代价是量化误差、码本训练及可能的精排开销                 |

还有`LSH`等方案，通过哈希将相近向量放入更有机会共同命中的桶。实际候选不必穷举全部算法，先比较与业务约束匹配、引擎支持成熟的方案。

`IVF`是在缩小“去哪里找”的范围，`PQ`是在压缩“用什么表示向量”。`IVF_FLAT`并不天然具有`IVF_PQ`的压缩收益；`HNSW`本身也不等于压缩，具体引擎可以另行结合量化。

## 先定基线，再选结构和参数

**先固定比较条件。** 使用相同的文档向量、查询集、距离度量、数据版本和权限范围。如果模型要求归一化，就按其检索约定处理文档与查询；不能让一组用余弦、另一组用未归一化内积，再把差异全部归因于索引。

**用精确搜索取得近邻基线。** 对每个查询，在符合过滤条件的向量集合中求精确`Top-K`，再看近似结果与其重合多少。这里衡量的是索引找回数学近邻的能力；这些近邻是否包含业务答案，还要通过人工标注的证据相关性和最终问答检查。两种“召回率”不能混用。

**在同一召回目标下比较成本。** 同时记录`P50/P95`延迟、并发吞吐、峰值内存、索引大小、构建时间，以及增删改的成本。只看默认参数下谁更快，可能是在比较不同的质量水平。

| 结构   | 优先观察的参数                                                        | 调整时需要验证什么                                                     |
| ------ | --------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `HNSW` | 连接规模M、构建探索范围、查询探索范围，如`efConstruction`、`efSearch` | 建图质量、连接空间、查询召回与延迟；查询扩搜无法直接修复建图连接       |
| `IVF`  | 桶数`nlist`、查询探查桶数`nprobe`                                     | 漏探近邻的比例、实际扫描向量数、桶分布与延迟；新增数据是否偏离训练分布 |
| `PQ`   | 子空间划分、码长、码本及是否保留原向量精排                            | 压缩后的排序损失、内存节省和精排读取成本                               |

这些参数是具体实现中的常见名称，默认值不是算法常数。图搜索的平均导航表现也不能写成任意数据下都保证`O(log N)`。

## 一个内存预算例子

假设有100万条768维向量，原始向量使用32位浮点数，单条占`768 × 4 = 3,072`字节，合计约3.07GB，即2.86GiB。这还不包含ID、元数据、图连接和服务运行开销。

若采用96个子向量、每个编号8位的`PQ`编码，码长为96字节，100万条编码约96MB，即91.55MiB；**仅向量编码部分**约为原始浮点向量的1/32。码本、ID、索引结构和可能保留的原向量还要另算，不能据此声称整个服务内存减少32倍，更不能跳过召回评估。

因此，内存紧张时压缩值得测试；若质量要求需要大量原向量精排，则还要计算额外存储与读取成本。

## 带过滤、更新的知识库要额外查什么？

比如用户只能查本部门文档，要检查引擎如何结合权限过滤与近邻检索：先缩小合法集合、搜索时限制遍历、候选后过滤或自适应切换，可能产生不同表现。过滤很强时，直接扫描很小的合法集合反而可能更合适。元数据索引帮助查找和估计过滤集合，与向量索引承担的职责不同。

高频更新场景还要核对删除可见性、索引重建、数据分布变化和写入期间的查询表现。`HNSW`支持增量插入，不代表所有实现都支持相同的删除和维护方式。

索引方案与数据库产品也要分开比较：选择`HNSW`并没有同时决定副本、持久化、权限和故障恢复方案。机制可以进一步看[HNSW如何实现近似向量检索](https://mianstack.com/question/q-0075)及[HNSW与IVF的取舍](https://mianstack.com/question/q-0189)。

## 常见追问

**把所有桶都查一遍，`IVF`就是精确搜索了吗？**

在没有其他候选裁剪、使用相同度量的前提下，`IVF_FLAT`探查全部桶，相当于覆盖全部原始向量，可以恢复精确检索的结果；但通常失去了少扫描的收益。`IVF_PQ`即使探查全部桶，仍有量化距离误差，除非另外用原向量对足够完整的候选做精确比较。

**提高索引召回率，RAG就一定更好吗？**

不一定。精确近邻可能本来就与答案证据无关。要分别判断索引近似误差、`Embedding`匹配质量和业务证据覆盖，再检查生成结果；不能把换索引当成所有检索问题的解法。
