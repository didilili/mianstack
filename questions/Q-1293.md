## 核心回答

模型应按任务的能力要求、质量标准、延迟成本和部署条件选择，再用同一批业务任务对比。品牌或公开榜单可以帮助筛选候选，但不能直接决定某个项目里谁最好。

- **分类、抽取、路由和简单问答：** 优先比较轻量模型或较低推理预算，检查格式、边界和响应速度是否达标。
- **复杂推理、编码和多步 Agent：** 比较更强的推理与工具使用能力，同时看任务完成率、错误恢复、调用次数和总耗时。
- **图片、图表或扫描文档理解：** 先确认模型支持所需模态，再测实际材料，不能只依据文本评测分数。
- **知识库问答：** 同时看模型能否利用证据、遵守条件和正确引用；资料缺失与检索错误要和生成能力分开。
- **有本地部署要求：** 比较可用权重、许可证、显存、量化和并发成本，模型能力与部署性能一起测。

具体比较时，固定任务集、成功标准和环境，记录准确版本、思考模式、上下文及工具配置；分别统计质量、稳定性、延迟和完成任务的总成本。高频简单任务与少量复杂任务可以采用不同模型，但路由策略本身也要验证。

## DeepSeek、千问和 Claude 可以怎样理解

下面用已公开能力举例，作为构建候选集的依据：

**千问：** 已公开权重的 `Qwen3-32B` 是文本模型，支持思考与非思考模式切换，也有工具使用能力。它可以作为需要本地部署、调整推理配置的候选；同一系列还有不同形态的模型，应按具体版本确认输入模态与能力。这个例子不代表千问系列的所有模型都使用相同配置。

**DeepSeek：** 当前 API 文档的思考模式支持工具调用，可以纳入复杂推理和 Agent 任务比较。接入时需关注思考强度、参数支持及工具轮次中的消息回传约定；这些条件会影响任务是否完整执行，不能只比较最终文本看起来是否聪明。

**Claude：** 截至 2026 年 10 月 17 日，官方概览将 Haiku 5.5 定位于高频、低延迟的分类、抽取和路由，将 Sonnet 5.5 定位于速度与能力的折中，将 Opus 5.5 定位于长时间 Agent 编码和知识工作。这些是厂商定位，适合据此选择要测的档位，具体业务表现仍由自己的任务验证。

因此，一份有用的比较结论应该是“某个版本和配置在哪类任务上表现更合适”，而不是给三家模型贴上永久不变的性格标签。项目具体模型 ID 和部署版本的说明，可结合[项目模型与版本核对](/question/q-0323/)。

## 比较之前，先确定测什么

把场景拆成可判断的任务。例如：

- 客服抽取：字段是否完整、类型是否正确，缺信息时是否追问。
- RAG 回答：关键结论是否被证据支持，是否混入旧版本和不存在的条件。
- 编码：需求对应的测试是否通过，是否破坏现有行为，是否产生无关改动。
- 工具 Agent：工具选择和参数是否正确，业务结果是否完成，遇到超时或缺信息能否恢复。
- 多模态理解：图表数值、结构关系和图片中的关键文字是否识别正确。

同一模型可能在其中某类任务上突出，在另一类上不合适。评测集应覆盖真实流量中的常见、边界和困难任务，保留一部分未参与 Prompt 调整的样例，按类别报告结果。

## 怎样保证横向比较有意义

**任务条件保持一致。** 使用相同需求、可访问资料、工具能力和成功标准。Agent 测试从干净状态启动，避免前一轮留下的文件、缓存或业务状态让后一轮获益。

**配置明确而且合理。** 保存模型 ID、服务平台、版本、Prompt、思考模式、输出预算和重试策略。各家参数语义并不相同，有些参数在特定模式下不会生效，因此公平比较应围绕任务条件和预算，而不是机械传入同一组温度等参数。可以分别报告统一基线与各模型合理调优后的结果，调优范围和投入也写清楚。

**区分模型比较与系统比较。** 若要看模型差异，先尽量固定检索结果和工具环境；若要判断上线方案，再比较模型与检索、Prompt、路由组成的完整系统。否则一次检索改进容易被误算成模型能力提升。

**处理运行波动。** 对关键任务重复运行，观察稳定性；不要只挑最好的一次。规则、测试和业务状态适合验证客观正确性，开放式表达可用明确评分标准、盲评或模型评审，并抽样校准。成对评审交换展示顺序，减少位置偏差。

## 质量之外还看哪些代价

延迟区分首个可用内容、完整回答和任务完成时间。模型返回处理进度或推理摘要，并不等于用户已经收到可用答案；Agent 单次生成很快，也可能因为工具循环多而使任务更慢。

成本应覆盖整个任务的模型调用、失败重试、工具和必要资源。单价较低的模型如果需要多次修正，完成一个有效任务的总成本可能更高。线上还应在目标并发下观察延迟分布、限流、超时与可用性；本地部署则同时记录硬件、量化和推理框架配置。

最终可以先排除无法满足功能或质量要求的候选，再在达标方案里比较延迟、费用和维护复杂度。公开模型卡提供能力范围和测试起点，真实任务结果决定最终取舍。

## 追问：是否应该为每个 Agent 配不同模型

不需要按角色数量机械增加模型。不同角色的任务难度、延迟和质量要求确实不同，分模型才有价值。例如路由使用较轻配置，复杂分析使用较强配置，前提是前者不会把任务误分到错误路径。

如果设计升级或回退机制，要定义触发依据，例如结构校验失败、信息不足或多次工具失败，并评估额外耗时、上下文转交和总成本。多个模型组成的方案也要作为整体测试，不能只把各自单独的最好成绩相加。
