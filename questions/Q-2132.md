> 在面栈阅读：[Agent 状态机如何管理？](https://mianstack.com/question/q-2132)

## 核心回答

Agent 状态机要同时管理**任务处于什么阶段、哪些事件允许它继续，以及恢复后怎样避免重复执行**。聊天记录提供上下文，状态机提供执行控制，两者需要关联保存。

常见任务状态包括待调度、运行中、等待输入或审批、重试等待，以及成功、失败、取消等终态。每次转移必须有明确事件和条件：依赖满足才能开始，工具超时按错误类型重试，缺少输入进入等待，结果通过验收才成功。运行时保存当前节点、关键业务数据、产物引用和预算，暂停或故障后从可恢复的检查点继续。

并发执行时，状态更新需要校验当前状态与版本；存在 Worker 接管时再校验执行者和接管代次。检查点只能恢复程序状态，外部写操作还要通过幂等键、业务唯一约束和执行回执防止重做。

## 展开说明

### 先把三类状态分开

| 类型         | 记录什么                                   | 作用                     |
| ------------ | ------------------------------------------ | ------------------------ |
| 任务生命周期 | 运行、等待、成功、失败、取消、尝试次数     | 决定能否调度、重试、接管 |
| 图与业务状态 | 当前节点、计划、资料、待审批参数、产物引用 | 决定后续节点需要处理什么 |
| 模型会话状态 | 用户消息、模型动作、工具结果及摘要         | 给下一轮模型提供上下文   |

例如“等待确认报告发布”是生命周期状态；报告文件和发布参数是业务状态；模型与用户的讨论是会话状态。只把整段聊天存入 `Redis`，并不能自动恢复待发布动作及其审批条件。

### 用事件和守卫条件推进

一种可行的设计是：

- 待调度收到执行事件，检查依赖和预算后进入运行中。
- 运行中缺少必要字段，保存缺口并进入等待输入；输入补齐且有效后重新调度。
- 调用出现瞬时错误，记录错误、尝试次数与下次执行时间，进入重试等待；永久性业务拒绝直接失败。
- 已保存结果且验收通过后进入成功。取消后拒绝新的普通执行事件，迟到结果不能把任务重新标成成功。

这些不是唯一一套状态枚举，重要的是终态、等待条件、错误分类和转移规则清楚。模型可以提出“需要补查”或“等待用户”的意图，运行时负责检查并提交真正的状态变更。

### “原子状态机”解决什么？

设两个请求同时读取“运行中，版本7”：一个提交完成，一个提交取消。如果都无条件覆盖，最后写入者就会抹掉前者。

可以在一次条件更新中同时检查任务ID、预期状态和版本，成功时写入新状态及产物引用，并递增版本。受影响行数为0表示发生了并发变更，需要重读，不能强行补写。若状态变化还要通知消息队列，可结合事务内 `Outbox` 等机制，避免状态已提交而后续事件丢失。

分布式接管还要防止旧执行者回来提交。租约判断何时允许接管，`Fencing Token` 让接受写入的一方拒绝旧代次；它不是仅存在日志中的编号。单进程、单执行者的简单流程不必预先引入全部分布式字段。

### 恢复不能只恢复聊天

检查点应能确定当前执行位置、已经确认的中间结果、待办动作、预算消耗以及恢复所需的配置版本。原始大文件放在产物存储，状态中保存引用。

恢复节点可能重新执行。尤其 `LangGraph interrupt()` 恢复时，含有中断的节点会从函数开头再次运行。因此审批前只做可重复的准备，审批后再进入独立执行节点；执行节点仍要有业务幂等保护。

例如创建工单的外部请求已成功、但本地还未保存回执就宕机，恢复时应以同一业务幂等键查询或重试，不能因为检查点里“尚未完成”就创建第二张工单。

## 常见追问

**状态机、`DAG`、`StateGraph` 是同一个概念吗？**

它们从不同角度描述执行。状态机强调事件驱动的合法迁移，`DAG` 强调无环依赖，`StateGraph` 用带状态的图组织节点与边，并可以包含循环。任务生命周期可以包在图外，图内部继续维护节点状态。

**内存 `Checkpointer` 能用于服务重启恢复吗？**

不能。它适合同一进程中的会话延续或调试。跨重启恢复需要持久化检查点、任务调度与接管逻辑，同时处理尚未确定的外部副作用。
