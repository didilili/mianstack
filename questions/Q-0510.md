## 核心回答

先把“响应慢”拆成**首次可见输出慢**和**整次生成结束慢**，再沿客户端、网络与网关、服务端排队、模型生成这条链路定位。只看一次接口总耗时，很难判断该压缩输入、缩短输出，还是处理连接、限流和排队。

我会用相同输入、模型与输出要求对照，记录首字、总耗时、输入输出 Token、缓存命中、并发、重试和错误。输入处理重就精简相关上下文、复用稳定前缀；生成长就控制答案范围，并评估更合适的模型；排队或限流重就调整并发与容量。流式返回可以改善等待体验，但仍需检查代理和前端是否及时展示，并单独验证完整结果的耗时与质量。

## 先把时间量清楚

从客户端发起请求，分别记录连接与请求发送、收到响应头或事件、首次可见文本、最后输出和连接结束。首个事件可能只是角色、状态或其他元数据，并不等于用户已看到文字；支持推理过程的模型，也可能在可见答案之前已经进行了计算。

客户端观察到的首字等待通常混合了网络、服务排队与输入处理，不能直接当作纯 GPU 计算时间。结合服务端指标、请求标识与供应商反馈，才能进一步分开。对有 RAG 或工具的应用，还应先把这些前置耗时与单次模型 API 调用区分，避免优化错层。

对照时固定任务、模型版本、输出要求与负载，并记录缓存与重试。可以先用最小客户端直接调用相同服务，比较经过业务网关和完整应用的情况，定位代理缓冲、连接复用、连接池等待或前端刷新问题。

## 输入、输出与调用方式分别怎样优化

**输入侧：减少无关工作。** 历史对话、检索片段和工具定义只保留本任务需要的部分，避免重复拼接。裁剪时保留权限约束、用户条件与证据，不能只按长度从头删除。服务支持上下文缓存时，可以把适用的稳定公共前缀组织在前面，再放动态问题，并通过返回统计检查命中。

上下文缓存复用的是输入计算，不是直接返回上一次答案。支持模型、匹配规则和有效期因服务而异；首次创建与未命中也有开销，不能因为内容看起来相似，就认定已经加速。

**输出侧：让生成长度匹配需求。** 简短分类或结构化提取，不要求模型先写长篇解释；长报告则可以按章节或阶段交付。设置输出预算时，仍需保证必要内容完整，处理截断与未闭合结构。模型支持推理预算等能力时，按任务质量进行评估，不能通过随意减少思考或换小模型就假定效果不变。

**调用侧：减少不必要的往返。** 检查是否为一个简单判断连续请求多次模型，或在异常后多层重试。可以合并真正兼容的步骤，独立请求设置有界并发；依赖前一结果的调用仍需保留顺序。模型选择和路由要用任务集对照，比较完成质量与总耗时，而不只比较一次生成速度。

## 流式、超时和并发的常见误区

流式让服务把已生成内容逐段交给客户端。只有服务、网关和页面都及时传递与刷新，用户才能更早看到文字；如果中间层等完整响应才转发，后端开启流式也不够。工具参数的中间片段还不完整，不能为了快就提前执行。

流式主要改变可见输出的时机，不保证整段生成更快。首字变快但总时长没变，仍可能改善体验；如果任务要求一次性完整 JSON 或批处理结果，则要同时考虑完整性和消费方式。

超时设置应覆盖连接、等待和整体任务预算，不能只缩短客户端等待就宣称服务已经变快。对可重试错误采用有限退避，记录实际尝试次数；持续过载时，增加并发或立即重试可能把队列推得更长。取消请求后是否停止服务端计算，也要按所用接口确认。

## 怎样验证结果

按相同任务和负载对照首字、完整耗时、P95 等尾延迟、超时率、输出完整性与答案质量，并记录输入输出和缓存变化。把流式展示改进、减少实际计算和扩容后的排队改善分别说明，才能知道哪个措施起了作用。
