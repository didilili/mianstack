> 在面栈阅读：[项目的 Harness 如何设计？](https://mianstack.com/question/q-2302)

## 核心回答

项目的 `Harness` 是模型外侧的执行系统，负责把“模型提出下一步”变成**有上下文、有边界、能验证和恢复的实际动作**。设计时沿一次任务，把输入组织、工具执行、状态与预算、验证反馈和失败恢复接起来。

可以抓五类职责：

1. **任务与上下文**：保存目标和约束，按当前阶段提供相关历史、资料与工具定义，大材料通过文件引用按需读取。
2. **动作执行**：把模型调用转换为受控工具请求，完成参数、身份、资源范围和副作用检查，回填真实结果。
3. **运行控制**：记录状态与检查点，限制时间、步数、费用和并发，支持取消、等待输入及恢复。
4. **验证反馈**：根据任务检查产物、业务规则或测试结果，把具体失败反馈给下一轮，而不是只依赖模型宣布完成。
5. **观测与迭代**：关联模型、工具、状态变化和产物，用实际失败轨迹改进上下文、工具接口和控制策略。

`ReAct` 描述行动反馈循环，`MCP` 提供工具接入协议，Harness 把这些能力连到可管理的运行环境中；它没有必须照搬的统一分层数。

## 以代码修复任务说明设计

下面是一个设计示例：用户要求修复某接口的空输入错误。

入口创建任务和工作区，固定可修改范围、复现输入及验收命令。上下文只包含相关模块、现有约定和失败日志。模型提出读文件、修改或测试等动作，执行器按工作区和工具策略执行，输出退出码、错误摘要和完整日志引用。

测试失败后，Harness 把失败用例、相关差异和上一轮尝试留给模型，继续修复；测试通过后检查变更范围及用户要求，再产生可审阅的补丁。写文件和运行测试是不同动作，产物存在、命令成功与任务验收也分别记录。

一次修改不一定需要多 Agent、长期记忆或复杂任务队列。先把复现、修改、验证和停止做清楚，长任务再增加摘要交接、持久化和独立验证器。

## 关键控制怎样落地？

| 环节     | 不能只写在提示词里的部分 | 可实施的控制                                   |
| -------- | ------------------------ | ---------------------------------------------- |
| 文件操作 | “只改这个项目”           | 路径解析、工作区边界、操作工具策略或隔离环境   |
| 工具结果 | “认真看错误”             | 返回错误类型、退出码、关键日志及原始结果引用   |
| 上下文   | “记住目标”               | 结构化任务状态、相关材料选择、摘要及可回读证据 |
| 循环     | “不要一直尝试”           | 总Deadline、调用/费用上限、重复无进展检测      |
| 交付     | “做完再结束”             | 对输入、补丁、测试和产物定义独立验收条件       |
| 恢复     | “失败后继续”             | 检查点、任务接管、动作幂等与未知回执核对       |

沙箱控制工具在哪里运行及能访问什么资源，工具策略控制允许哪些动作，两者共同构成执行边界。敏感身份、凭证与权限从可信运行环境注入，网页或工具输出中的指令不能获得同等权限。

## 一次失败与恢复怎样讲清？

假设测试工具运行超时。Harness 应记录对应进程或远程任务句柄，先确认仍在运行、已结束还是结果未知；若仍在运行就按策略取消或继续观察，不立刻重复启动第二份。

任务因进程故障中断时，从检查点恢复目标、已确认改动、产物和预算。模型调用和某些节点可能重新执行，涉及创建工单或发布操作时，还需查询回执并使用幂等键。保存了检查点并不能跨数据库、工具服务自动形成一次完整事务。

## 常见追问

**Harness和Runtime有什么关系？**

Runtime通常强调调度、状态、事件与执行生命周期；Harness强调围绕模型的完整工作环境，包括上下文、工具、策略和验证。具体项目可能把二者放在同一组件，也可能分层实现，回答时应说明实际职责。

**Evaluation Harness也一样吗？**

它主要负责组织样本、运行被测对象、评分与记录，衡量系统是否完成任务。生产Harness产生执行轨迹，评测Harness可以回放或分析这些轨迹，两者能共享工具，但目标不同。

**怎样证明改进有效？**

固定一组真实失败任务，保持模型与任务条件可比，只改变某个工具接口、上下文或策略。比较任务完成质量、错误类型、耗时和费用，并检查恢复是否产生重复动作；不能只用提示词变长或模块变多证明改善。
