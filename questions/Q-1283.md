## Pi（TypeScript）

### 核心回答

`Pi Coding Agent` 是基于 `TypeScript`、运行于 `Node.js` 的可组合编程助手。它把模型适配、Agent 运行循环和编程会话分开：`pi-ai` 统一模型消息与流式协议，`pi-agent-core` 组织模型请求、工具执行和结果回填，`pi-coding-agent` 在上面提供仓库工具、会话持久化、分支、压缩及扩展能力。

一次任务中，模型根据当前上下文提出工具调用，运行时执行工具并回填结果，再请求模型决定下一步。长任务的历史保存为会话树，模型只读取活动分支经过投影和压缩后的内容；团队需要的工具、提示词和运行规则可通过 `Extension` 接入。这使核心循环可以复用，终端、`RPC` 和 `SDK` 则承担不同的交互与集成方式。

### 各层怎样分工？

- **模型适配层 `pi-ai`：** 提供模型描述、结构化消息、工具声明、流式事件和最终响应，再由供应商适配器处理实际请求与响应协议。上层不用逐家解析流，但不同模型的能力、错误和调用质量仍可能不同。
- **运行循环 `pi-agent-core`：** 管理当前消息、可用工具与运行状态；调用模型、执行工具、追加结果，并处理用户插入的新指令、后续消息和中断。它不等于会话文件管理器。
- **编程会话层 `pi-coding-agent`：** 组合项目上下文、读写与命令工具、模型设置和资源加载，把消息写入 Session，提供树导航、压缩和 Extension。
- **交互层：** `pi-tui` 提供终端组件，交互模式展示运行事件；`RPC` 通过标准输入输出交换 `JSONL`，`SDK` 则让 Node.js 程序直接创建和控制会话。

模型接口、循环和会话可分别复用，产品入口也共用会话与运行机制。

### 一次请求怎样完成工具闭环？

以“读取 README 并概括项目”为例，第一次模型请求携带用户消息和 `read` 工具定义。模型返回带调用 ID 的工具调用，循环按工具名找到实现、处理参数并执行，生成带相同 ID 的 `toolResult`。下一次请求加入这个结果，模型才能根据真正读到的文件回答。

这段闭环有两个关键边界：**工具调用表示模型想做什么，工具结果才表示执行观察到了什么；模型停止生成也不等于开发任务已经验收。** 文件修改是否正确、测试是否覆盖需求，仍要根据真实文件和命令结果判断。

[运行循环](https://github.com/earendil-works/pi/blob/58c0b02ce552adab76014e7ed712ab7981359aa8/packages/agent/src/agent-loop.ts#L250-L322)把工具结果追加回上下文，再判断是否需要下一次请求。模型错误或中断会结束当前循环；输出长度达到限制时，可能不完整的工具调用参数会被转成失败结果，避免直接执行半截调用。

流式文本、工具开始和结束等事件用于驱动界面和宿主程序；Session 中的消息、调用和结果用于后续重建。不能只保存屏幕上的文本增量，却丢掉工具调用 ID、错误和完整结果。

### 为什么会话历史和模型输入要分开？

Pi 的持久 Session 是追加式 `JSONL` 文件。消息、模型切换、摘要等条目都有 `id` 和 `parentId`，形成会话树；当前 `leaf` 表示选中的位置。返回旧节点后继续追加，就能保留方案 A，再尝试方案 B，而不用覆盖原来的记录。

模型输入从当前叶子沿父指针回到根，只采用这条活动路径。切换分支时，可以选择将离开路径到共同祖先之间的内容生成分支摘要，并挂到目标位置；没有选择摘要时，其他分支的发现不会自动全部带过来。会话导航改变的是对话路径，不会把工作目录中的文件一并回滚。

[上下文投影](https://github.com/earendil-works/pi/blob/58c0b02ce552adab76014e7ed712ab7981359aa8/packages/coding-agent/src/core/session-manager.ts#L468-L582)进一步处理压缩和上下文编辑：原始记录保留，模型看到的是当前路径中实际有效的消息。`context_edit` 可以追加一条编辑记录，替换或省略旧消息对模型输入的贡献，而不改写原始消息。这便于保留历史依据，同时减少过期或无用内容对后续判断的影响。

### 长任务怎样压缩？

Pi 结合最近一次模型用量和后续新增消息估算上下文，当接近模型窗口预留边界时触发压缩，也支持手动压缩。它将摘要及保留起点写成新的 `compaction` 条目，后续请求采用摘要、近期保留消息和新增消息，旧记录仍留在会话文件中。

切分时要维护工具调用与结果的配对关系，不能为了达到一个 Token 数就从工具结果中间截断。较大的交互可能需要单独总结前半段，同时保留后半段继续执行。[压缩准备](https://github.com/earendil-works/pi/blob/58c0b02ce552adab76014e7ed712ab7981359aa8/packages/coding-agent/src/core/compaction/compaction.ts#L859-L922)基于模型可见的投影选择这些范围；上下文编辑或压缩使旧用量失效后，也需要重新估算。

压缩摘要和分支摘要解决的问题不同：前者减少当前路径的输入，后者把离开分支的有用发现带到新位置。两者都有信息损失风险；精确错误、关键约束和文件状态应能回到原记录或实际环境核对。

### Extension 能怎样接入运行过程？

`Extension` 是运行在 Pi 进程内的 TypeScript 模块，可以注册工具、命令及事件处理器。例如，在运行开始前调整提示词，在工具调用前返回阻止结果，在工具返回后整理内容，或定制分支摘要和压缩行为。

请求前的上下文钩子有两层：[普通 `context`](https://github.com/earendil-works/pi/blob/58c0b02ce552adab76014e7ed712ab7981359aa8/packages/coding-agent/src/core/extensions/runner.ts#L1300-L1366)处理对话消息，Pi 会恢复系统提示与工具声明；`context_with_system` 处理包含系统消息的完整输入，扩展要自己维护提示词和工具声明。这些请求时的变换不会自动改写持久历史。

扩展状态同样要区分用途：`custom` 条目用于保存程序状态，默认不进入模型上下文；`custom_message` 才用于注入模型需要知道的内容。只需要提供操作知识时可以使用 `Skill`，不必写成扩展代码；需要运行时执行和拦截时再使用 Extension。

这种设计把工作流定制留给扩展，但扩展与工具仍受所在进程的权限影响。钩子拦截、项目信任和操作系统隔离各有职责，不能把“支持扩展”当成默认沙箱或完整权限保证。
