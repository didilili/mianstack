> 在面栈阅读：[Agent 记忆压缩有哪些方法，如何选择？](https://mianstack.com/question/q-4343)

## 核心回答

Agent 记忆压缩通常组合使用**删除无关内容、选取关键原文、摘要旧历史、抽取结构化状态，以及外置后按需检索**。前几种直接减少本轮输入，外置则把不必常驻的细节留在窗口之外，需要时再取回。

选择依据是后续任务需要什么：短期交流重视原话，保留近期窗口；长流程重视目标和进度，用摘要与任务状态；金额、日期和授权确认需要精确值，保留原文或结构化记录；大量日志与资料适合外置并按问题检索。常见组合是近期原文、阶段摘要和可回读原始记录，而不是用一份越来越短的摘要取代所有历史。

压缩效果要看任务连续性和信息损失，再看 token 与成本，不能只比较压缩率。

## 各种方法的取舍

| 方法         | 主要做法                         | 适用情况                   | 代价与风险                     |
| ------------ | -------------------------------- | -------------------------- | ------------------------------ |
| 滑动窗口     | 只发送近期完整交互               | 近期依赖强、任务较短       | 早期约束可能退出窗口           |
| 关键片段选择 | 按相关性或重要性保留原文         | 需要保留精确条件、局部证据 | 筛选错误会漏掉反例与上下文     |
| 摘要压缩     | 将早期过程归纳为较短文本         | 长对话、已结束阶段         | 可能遗漏、改写或累积漂移       |
| 结构化抽取   | 提取目标、实体、决策、待办等字段 | 固定业务状态、多步执行     | 字段设计不全会丢掉未建模细节   |
| 外置与检索   | 原文放文件或数据库，按需回读     | 长日志、文档、历史材料     | 增加读取延迟，检索也可能漏召回 |
| 上下文隔离   | 子任务独立执行，只回传必要结果   | 可拆分的调查与代码阅读     | 交接摘要可能丢掉约束和来源     |

这里的“语义压缩”通常指用更短的表达保留任务相关含义，并非无损编码；外置与隔离严格说是上下文管理方式，也经常与记忆压缩一起使用。`SQLite`、`Redis`、向量索引或倒排索引提供存储/查询能力，本身不是摘要算法。

## 一个长任务怎样组合？

假设 Agent 在排查订单超时，已经读过多轮日志。当前需要继续定位数据库等待，可以保留：

- 近期原文：最新错误与正在分析的调用结果。
- 任务状态：目标接口、复现条件、当前假设、已排除项与下一步。
- 阶段摘要：此前查到的关键事实及对应日志位置。
- 外部记录：完整日志和历史尝试；需要比较特定请求时再按请求 ID 取回。

这样后续不必反复读取所有日志，又能够回到原始证据。若下一步要比较精确耗时，就取回原始时间戳，不能用“数据库有点慢”的摘要替代。

## 摘要本身怎样压？

可以按“当前目标、有效约束、已确认事实、已做动作、未完成事项、证据位置”组织。明确区分观察结果、猜测和计划，用户修订过的条件保留最新值及替代关系。

增量摘要只处理新增区间，减少反复加工全文的成本；但如果一直只基于上一版摘要继续压缩，早期遗漏可能无法恢复。因此保留原文与覆盖区间，并在关键事实变化或摘要冲突时回读重建。

对已消费的大工具结果，先去掉重复内容、空白、无关行或只保留错误附近片段，往往比再次调用模型总结更直接。精简规则也要经过任务验证，避免把必要的否定条件和失败分支一起删掉。

## 如何决定采用哪一种？

先标注任务必须保留的信息，再固定一组长轨迹比较方案。检查早期约束是否仍生效、更正是否覆盖旧事实、执行状态是否准确、精确数字能否恢复、最终任务能否完成；然后统计输入token、额外摘要与检索调用、总时延及费用。

如果经常回读同一段原文，可以提高它的常驻优先级；若摘要丢失某种条件，就调整摘要结构或保留必要原句。窗口接近上限前提前处理，为摘要请求和下一次工具结果留出空间，没有跨模型通用的固定触发百分比。
