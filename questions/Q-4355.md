> 在面栈阅读：[压缩多轮对话后，如何拼接用户消息、模型消息与摘要？](https://mianstack.com/question/q-4355)

## 核心回答

基本结构是：**有效指令＋明确标记的历史摘要＋近期完整消息＋本轮新输入**。摘要替代它已覆盖的旧历史，近期消息保留原来的角色和先后顺序，而不是把所有内容拼成一条用户消息。

具体有四点：

1. **指令与历史分开**：系统规则仍由应用加载；摘要注明来自先前对话，不把模型归纳出的内容提升为新的系统命令。
2. **用明确边界替换旧历史**：保存摘要覆盖到哪个消息 ID、从哪里开始保留原文，避免一段内容既在摘要里又整段重复注入。
3. **保留近期交互结构**：`user`、`assistant` 和工具结果按时间顺序排列，工具调用与结果通过调用 ID 对应，不能只留下结果却删掉调用。
4. **最后加入本轮输入并重新算预算**：新的用户问题放在近期历史之后；工具执行中的下一轮则按实际顺序接入工具结果。预算仍不足时，继续调整旧历史或大结果，不能截断正在进行的工具交互。

摘要中保留目标、有效约束、已确认事实、决定和未完成事项，并带原始证据位置。摘要与最新原文冲突时，应回查对应记录并更新状态，不让旧摘要反复覆盖用户更正。

## 一个消息顺序示例

下面表示一次新用户问题到来时的上下文结构，摘要的具体承载角色由框架与提供商接口决定：

```text
system：当前有效的规则与工具说明
历史摘要：先前任务、已经确认的决定、未完成项和原文位置
user：近期提出的排查要求
assistant：调用 read，调用 ID 为 call_1
tool：call_1 的读取结果
assistant：依据读取结果给出的判断
user：本轮新问题或更正
```

若切分点落在 `assistant` 的工具调用与结果之间，应把两者一同保留，或把已完成的整组交互归入摘要。不能把旧工具返回伪装成新用户命令，也不能编造一条“执行成功”来补齐缺失结果；缺失结果应按执行状态核对和恢复。

## 连续压缩怎样避免越拼越乱

为摘要保存版本、覆盖范围和近期原文起点。下一次压缩时，更新“已有摘要＋新增的待压缩历史”，成功保存后再推进边界；旧摘要不作为另一条独立结论再次叠加。原始记录继续保留，金额、版本、路径和执行状态有疑问时可回查。

原始会话是完整记录，模型输入是当前任务所需的投影，两者可以不同。尤其是树形会话，先选择当前分支，再处理摘要与近期消息，不能按文件追加顺序把其他分支也全部塞进去。消息格式合法之外，还要验证关键约束、用户更正及未完成事项是否在压缩后仍可使用。

## Pi（TypeScript）

`Pi 1.4.0` 将会话保存为带 `id`、`parentId` 的条目树。模型输入由当前分支投影生成：**当前路径上的最新压缩摘要＋保留的近期条目＋压缩后的新增条目**，并应用该路径上的上下文编辑。

### 先选路径，再应用压缩边界

`buildSessionPath()` 从当前叶子沿 `parentId` 回到根，再反转为执行顺序；它不会遍历所有兄弟分支。`buildContextEntries()` 找到这条路径上最新的 `compaction`，把该条目放在最前，然后接上：

- 从 `firstKeptEntryId` 开始、位于压缩条目之前的保留内容；这段中的旧 `system` 消息会被排除。
- 压缩条目之后、本分支新增的内容。

压缩条目保存了 `systemMessage` 时，投影先恢复这份提示与工具状态快照，再放摘要。即使较旧的压缩条目仍落在保留范围里，也不会再次注入旧摘要，因此不会出现多份历史摘要层层堆叠。

### 保留原角色，摘要明确标记为历史

普通消息保留 `user`、`assistant`、`toolResult` 等角色。内部的 `compactionSummary` 经过 `convertToLlm()` 转成 `user` 角色的文本消息，并带有明确的“此前历史已压缩为以下摘要”前缀与摘要标签。这里使用 `user` 作为兼容接口的载体，不表示摘要是用户刚发出的新要求。

默认压缩准备会避开工具结果作为切分起点，保留它前面的模型工具调用；若一个用户请求本身过长而需要从中间切开，则另做该请求前半段的摘要，接上后半段消息，而不是硬保留整个超长请求。

### 上下文编辑不改写原始会话树

`context_edit` 通过目标条目 ID 替换其上下文 `content`，或用 `replacement: null` 使它不进入模型输入；同一目标采用当前有效范围中最后一次编辑。原始条目、角色与其他元数据继续留在记录里，编辑只影响投影。

因此，界面和历史工具能看到的完整过程，不等于模型这一轮收到的内容。扩展省略工具调用或结果时仍需维护对应关系；投影机制本身不意味着任何任意删改都符合提供商消息要求。切换会话分支也只改变对话路径，磁盘文件或外部动作需要另行核对，不能视为已经回滚。
