> 在面栈阅读：[Function Calling、Skill 与 MCP 分别解决什么问题，如何组合使用？](https://mianstack.com/question/q-7073)

## 核心回答

`Function Calling`、Skill 和 `MCP` 解决执行链上的不同问题，可以组合，也可以分别使用。

- **`Function Calling`** 让模型按工具定义输出调用意图和结构化参数，应用再校验、执行对应函数，并把结果返回模型。
- **Skill** 封装完成一类任务的方法，包括适用条件、步骤、规则及可选脚本和资料，帮助 Agent 知道怎样组织任务。
- **`MCP`** 是宿主接入外部工具、资源和提示模板的协议，让不同服务用共同的发现与调用方式连接到应用。

例如审查一个 PR：Skill 规定先读改动、检查关键风险、再生成报告；模型通过 `Function Calling` 请求“获取 PR diff”；宿主中的 `MCP` 客户端把请求转发给 Git 服务，取得结果后继续审查。真正执行、认证和权限检查由应用及服务端承担。

## 三者怎样区分？

| 对象               | 主要解决的问题                       | 通常承载什么                                 | 不自动负责什么                   |
| ------------------ | ------------------------------------ | -------------------------------------------- | -------------------------------- |
| `Function Calling` | 模型如何表达要调用哪个能力及其参数   | 工具名称、参数 Schema、调用请求与结果关联    | 真实执行、访问授权与业务正确性   |
| Skill              | 一类任务如何执行与验收               | `SKILL.md`、流程、边界、脚本、资料与模板     | 工具安装、账号权限与强制状态控制 |
| `MCP`              | 应用如何以统一协议发现并接入外部能力 | 客户端/服务端消息、Tools、Resources、Prompts | 模型如何推理、任务如何规划       |

`Function Calling` 并不要求函数运行在远程服务。应用直接执行本地的 `calculate_total()`，也可以完成一次工具调用。

`MCP` 同样不是模型内置的网络理解能力。宿主建立连接、取得工具描述，再适配为模型能够使用的工具格式；具体模型无需自己实现 `MCP` 客户端。

## 用代码审查串起一次调用

1. 用户提交 PR 地址与审查范围，Agent 选择并读取代码审查 Skill。
2. 技能规定需要检查变更范围和相关调用路径。宿主已经通过 `tools/list` 等机制发现 Git 服务提供的工具，将所需名称与 `inputSchema` 暴露给模型。
3. 模型生成类似 `get_pr_diff` 加 PR 标识的调用请求。宿主校验参数、身份与权限，再通过 `MCP` 的 `tools/call` 请求服务端。
4. 服务端获取 diff 并返回结果；宿主按模型接口的要求关联调用与结果，Agent 继续阅读相关文件或调用测试工具。
5. Agent 根据技能中的标准形成问题报告。是否发布评论是另一项有副作用的动作，应使用对应权限与执行规则。

其中 `get_pr_diff` 只是示例工具名；不同服务端提供的名称和参数各不相同。工具结果过长时，应按任务读取片段，而不是把整个仓库一次送入模型。

## 怎样组合才合适？

只有一个稳定的内部接口时，直接定义函数并使用 `Function Calling` 就很清楚。需要多个宿主共享数据库、Git 或文件服务时，`MCP` 有助于统一接入；重复出现的专业流程再沉淀为 Skill。

纯写作 Skill 可以不调用任何外部工具；本地函数调用可以没有 `MCP`；一个 `MCP` 工具也可以在没有 Skill 的任务中被调用。不存在所有任务都必须经过“`Function Calling` 升级成 `MCP`，再升级成 Skill”的顺序。

上下文成本也要按实际实现衡量。Skill 可以渐进加载，`MCP` 工具也可以由宿主筛选和延迟暴露；不是协议规定所有工具定义必须一次塞入上下文。
