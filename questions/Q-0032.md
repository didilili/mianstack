> 在面栈阅读：[GPU 的存储层次和计算单元如何组织？](https://mianstack.com/question/q-0032)

## 核心回答

以`NVIDIA CUDA` GPU为例，芯片由多个**SM（流式多处理器）**组成。SM内有warp调度器、寄存器文件、加载/存储单元以及FP/INT计算单元、`Tensor Core`等；不同芯片的数量、指令与存储容量不同。`CUDA`把kernel线程组织成grid和block，block驻留在SM上，线程按通常32个组成的warp调度执行。

存储从靠近计算端的寄存器、SM内共享内存/L1，到全芯片共享的L2，再到片外设备显存`HBM`或`GDDR`。优化的核心是**让数据少搬、搬得连续、搬来多次复用**，同时避免寄存器或共享内存用量过大压低并发驻留能力。SM、`Tensor Core`和`CUDA`线程是不同层次，不能一一对应。

## 存储层次与访问范围

| 层次            | 常见物理位置与作用                       | 谁使用、谁管理                                     |
| --------------- | ---------------------------------------- | -------------------------------------------------- |
| Register        | SM片上寄存器文件，保存变量、索引、累加值 | 逻辑上线程私有，由编译器分配；占用影响驻留线程数   |
| `Shared Memory` | SM片上、可寻址的高速暂存区               | 通常block内线程协作显式读写与同步                  |
| L1 Cache        | SM附近的硬件缓存                         | 缓存相应访问；常与shared共享片上物理资源但语义不同 |
| L2 Cache        | 全GPU多个SM共享的片上缓存                | 硬件管理，减少对片外显存访问                       |
| `Global Memory` | 设备显存，常为`HBM`或`GDDR`              | 设备线程可访问，容量较大，延迟和带宽成本更高       |

`HBM`不是L2，也不是SM内部shared。shared是软件组织复用的数据空间，L1/L2是硬件管理的缓存；即使共享一块片上容量，也不能因此说两者是同一个接口。

`CUDA`中的**local memory**表示线程私有的地址空间，常用来存放寄存器放不下或无法寄存器化的数据，通常由设备显存承载并经缓存访问，不等于“线程附近的高速片上内存”。具体溢出策略还受编译器和架构支持影响。

主机内存与设备显存的传输又是另一层。`Pinned Memory`是页锁定的主机内存，可用于相应异步拷贝与DMA路径；它不是GPU block的shared。框架在CPU线程或stream中异步提交任务，也不表示CPU执行了GPU矩阵运算。

## 线程怎样落到计算硬件

一个grid包含多个block；一个常规block的线程驻留在同一个SM，多个block可同时驻留于一个SM，前提是线程、寄存器、shared等资源都够用。SM的warp调度器从就绪warp中发出指令，用其他warp的工作隐藏访存等延迟。

常见的128或256线程block分别含4或8个warp，便于按warp对齐并提供一定并发，但不是所有kernel的最优值。设教学例SM有65,536个32位寄存器，一个block有256线程、每线程占64个寄存器，则该block需16,384个，单看寄存器最多驻留4个block；还要受shared、线程数和硬件block上限共同约束。这是假设容量算例，不是所有GPU的统一规格。

分支分化会使一个warp的不同活动线程走不同执行路径，降低有效吞吐；需要同步时也不能凭“同warp通常一起运行”随意省略同步契约。

## CUDA Core、Tensor Core分别做什么

`CUDA Core`通常指通用标量算术执行通路中的计算单元，支持相应浮点或整数操作；`Tensor Core`面向矩阵乘加等特定指令，用支持的数据类型和布局提供高吞吐。`Tensor Core`在SM内与其他单元协作，不是另一个完整SM，也不是每个软件线程独占一颗`Tensor Core`。

矩阵乘法能使用`Tensor Core`的前提是指令、精度、布局和尺寸适配；索引、加载、`softmax`等仍需要其他执行通路。Hopper等架构还增加`TMA`等数据搬运机制，它们帮助供数，不能替代算术计算本身。

## 怎样用这个结构解释优化

矩阵乘法分块时，先让线程连续读取global中的数据到shared，block内多次复用，再把部分结果放寄存器累加，最后写回。两个16×16的`FP32`输入tile共需 `2×16×16×4=2048 bytes` shared；收益来自复用，而非shared本身扩大了总显存。

随后看实际瓶颈：global读写是否合并、shared是否bank冲突、寄存器是否溢出、occupancy是否受资源限制、`Tensor Core`是否被有效供数。occupancy高不等于性能必然最好；适度增大tile可能增加复用，同时减少活跃block，需比较真实kernel时间。
