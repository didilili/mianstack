## 核心回答

选择 Agent 的理由，是任务需要根据运行中的新信息决定下一步：查哪个来源、调用什么工具、是否补查或改变方案。它把模型的判断与真实执行、结果反馈连成循环；如果路径已经清楚，一次模型调用或固定 Workflow 就能稳定完成，应优先采用更简单的方案。

这几种方式可以组合。Prompt 决定怎样向模型描述任务，Workflow 控制明确的步骤和分支，Agent 在允许的范围内动态决策。项目选型要具体回答：**开放了哪项决策，模型实际采取过哪些不同动作，得到什么收益，又付出了多少延迟、费用与维护成本。**

以技术调研为参考：固定查询一份材料并总结，可以直接检索后调用模型；若需要根据资料中的新版本、缺失证据或相互矛盾的结论，决定继续查文档、比较数据并调整研究方向，Agent 才有更明确的作用。最后生成文件、检查格式等稳定步骤，仍可以交给程序或 Workflow。

## 先把比较对象说清楚

“Prompt 加大模型”本身并不与 Agent 对立，Agent 同样依赖提示和模型。这里比较的是：一次或少数几次预先安排的调用，能否完成任务，还是需要持续观察环境并决定后续动作。

一次调用适合输入已经齐全、输出目标清楚的任务，例如提取字段、分类或对给定材料做摘要。需要实时数据时，可以由程序先取数据，再调用模型，不必因此引入动态循环。

Workflow 适合依赖和分支相对稳定的过程，例如检索、重排、生成、格式校验；它也可以包含 LLM 节点、条件判断、循环、重试和并发，节点结果不一定是确定的。Agent 的区别在于把更大范围的行动选择交给模型，而不是“有循环就是 Agent”。

## 项目里，Agent 到底多做了什么？

以上述调研为例，用户要求比较两个方案的兼容性与部署代价。Agent 可以在读取初步资料后发现某项能力只在新版本存在，于是补查对应版本说明；发现两篇材料结论冲突，再核对发布时间、测试条件和原始来源；某个渠道没有证据，则换渠道或明确留下缺口。

关键在于这些后续动作由当前证据触发，行动的对象、顺序和停止时机随任务变化。执行记录应能显示“看到了什么信息，因此选择哪个动作，结果如何影响下一步”。只把固定的三次接口调用换成 Agent 框架，不能说明获得了这种收益。

动态决策也有范围。可以限定可用数据源、工具和预算，由程序负责参数检查、权限、执行与结果保存；模型负责选择下一步，不代替这些工程职责。研究方向的调整可以动态进行，产物生成和必要校验仍保留清楚的执行顺序。

## 怎样证明新增复杂度值得？

先建立能解决大部分问题的简单基线，例如单次检索加生成，或带有限分支的 Workflow。用同一批代表性任务、资料和验收要求，对比 Agent 在什么场景减少了漏查、错误结论或人工补充，再看完整任务的耗时、调用量、费用及失败处理成本。

最好把任务分组：固定资料问答、需要补充一次查询的任务、需要多轮探索的任务。若收益只出现在第三组，可以只让这类任务进入 Agent，其他请求沿用更短的路径。若核心问题是缺文档、工具不可靠或提示不清，先修这些问题，增加自主循环未必有效。

对照还要尽量可比。不能给 Agent 更强的模型、更多工具和更大的预算，再把全部改善归因于架构。若必须采用不同配置，应分别说明模型、工具与执行策略的变化。

## 面试官认为没必要用 Agent，怎么回答？

先回到项目事实，说明原流程在哪个节点遇到了变化、固定方案为何难以经济地覆盖，以及 Agent 承担的具体决策。例如“初次检索后依据缺失项决定补查哪个来源，得到证据后再调整比较范围”，比“模型会自主思考”更有说服力。

如果实际流程就是固定取数后总结，也可以判断当前 Workflow 更合适，解释为什么保留或简化实现。选型能力体现在能用证据调整方案，而不是一定要为 Agent 这个名称辩护。

## 常见追问

**分支都可以继续写进 Workflow，为什么还要 Agent？**

确实可以。应比较新增任务变化时的开发维护成本，以及模型动态选择是否达到需要的质量。有限且稳定的分支适合显式表达；变化方向多、需要持续理解中间材料时，可以在局部使用 Agent。不存在必须证明“任何代码都写不出来”才可以采用 Agent 的条件。

**更大的模型能不能一次完成所有规划？**

它可以提出更好的初始计划，但尚未执行的查询结果、环境变化和工具故障仍然未知。后续是否需要重新判断，取决于任务反馈，而不只取决于参数规模。如果输入已经完整，强模型一次完成也可能是更好的方案。

**用了 Agent，会不会更难控制？**

开放行动选择会增加路径和输出的不确定性，所以需要明确任务状态、工具结果、终止条件与运行预算。复杂度应与实际收益匹配；可以收窄决策范围、减少工具，或把成熟稳定的步骤收回明确流程。
