> 在面栈阅读：[项目工作流怎样划分步骤，并组织输入、状态与输出？](https://mianstack.com/question/q-8710)

## 核心回答

以下用基于 `shopkeeper-agent` 的“门店经营分析助手”设计案例说明：把经营问题转换为`SQL`并返回数据，门店口径和权限适配属于业务扩展。

工作流按**能独立说明输入、处理和输出的职责**拆分，而不是每调用一次模型就算一步。该路线先抽取问题关键词，再并行召回字段、指标和字段取值；合并补全上下文，过滤候选表与指标，补数据库和日期信息，然后生成`SQL`、校验并执行，最后经`SSE`返回过程与结果。

`LangGraph State` 保存问题、关键词、三路召回结果、`table_infos`、`metric_infos`、`SQL`及错误；数据库连接、检索仓库等依赖放在运行时`Context`。节点返回各自负责的更新，边规定先后依赖，校验结果决定执行还是纠错。

## 各步骤交付什么？

例如用户问“统计上月华东各门店净销售额”。在这个设计案例中，净销售额约定为本期实收减本期实际退款，退款按发生时间归属。

| 阶段             | 输入                    | 输出与下游用途                                               |
| ---------------- | ----------------------- | ------------------------------------------------------------ |
| 关键词抽取       | 原始问题                | 门店、区域、指标和时间等检索线索                             |
| 三路召回         | 问题及关键词            | 字段候选、指标候选、实际字段取值候选                         |
| 合并与补齐       | 三路结果及元数据        | 去重字段、补指标依赖、补取值示例，按表整理上下文             |
| 过滤与额外上下文 | 候选表、指标            | 收敛后的`table_infos/metric_infos`，加日期、数据库方言和版本 |
| `SQL`生成        | 问题及完整上下文        | 候选`sql`                                                    |
| 校验与分支       | `SQL`及数据仓库访问能力 | 校验错误或可执行分支；错误供纠错节点消费                     |
| 执行与返回       | `SQL`                   | 查询结果或明确执行错误，并通过`SSE`交付                      |

字段和指标通过 `Qdrant` 语义检索，字段取值通过 `Elasticsearch` 检索；元数据 `MySQL` 用于补表、字段和指标资料，经营数据 `MySQL` 用于`SQL`校验与执行。这两个`MySQL`职责应在排障和计时中区分。

## 为什么这样划分并行与汇合？

关键词抽取完成后，三路召回都有所需输入，并且分别写 `retrieved_column_infos`、`retrieved_metric_infos`、`retrieved_value_infos`，适合并行；`SQL`生成依赖合并、过滤后的完整上下文，不能在某一路结果尚未到达时提前生成。

合并节点不只是拼接文本。它按字段ID去重，补齐指标依赖、取值示例和候选表主外键，最终形成生成`SQL`所需的结构化上下文。主外键被补进来有助于连接推理，但不能保证任意跨表问题都能找到正确连接路径。

并行节点应该写不同字段，或明确`Reducer`。这里的候选召回与最终表上下文是不同阶段的数据，不宜让所有节点都覆盖一个名为 `result` 的自由文本字段。

## State与Context怎样分？

`State`保存要跨节点传递、需要复盘的问题和中间结果。例如纠错节点读取原`SQL`及 `error`，生成新`SQL`，后续继续消费；单个函数里的临时变量无需全部写进`State`。

运行时`Context`放数据库Repository、`Embedding`客户端等执行依赖，使节点能读取能力而不把连接对象塞入可保存的状态。业务身份和允许门店范围也应来自可信入口，在执行层约束；仅让模型生成门店 `WHERE` 条件不能独立承担访问控制。

最终输出应区分数据结果、采用`SQL`、业务口径和错误。底座使用 `runtime.stream_writer` 输出过程事件，API通过`SSE`传递，进度到达不代表`SQL`已经正确执行。

## 失败分支要沿实际边讲清

固定底座的 `validate_sql` 失败后进入 `correct_sql`，而纠错节点直接连到 `run_sql`，没有再次校验。当前校验执行 `EXPLAIN`，也没有分析执行计划；语法或解析成功并不能证明净销售额等业务口径正确。

更稳的改进是“纠错 → 复验 → 通过后执行”，同时限制纠错次数，设置无法修正的失败出口。校验范围还应包括只读语句、访问表和门店范围等执行约束。这是针对当前缺口的改进设计。

验证该工作流，应保留问题、指标定义、召回结果、最终上下文、`SQL`和执行结果，用跨月退款、部分退款、多表连接及越界请求检查每一阶段是否把约束正确传下去。结果对照看业务等价性，不只比较`SQL`字符串。

## 常见追问

**拆得越细越好吗？**

不是。值得独立观察、复用、重试或控制权限的步骤适合拆开；很小的局部处理可以留在同一节点。节点过细会增加状态字段和调度复杂度，过粗则难以定位是哪一步丢失了条件。

**为什么`SQL`生成前还要过滤？**

检索阶段追求找到候选，候选未必都相关。过滤和依赖补齐共同决定模型实际看到的上下文：减少无关表，同时保留计算指标和连接所需字段。它直接影响生成质量，不能把召回数量越多当作越好。
