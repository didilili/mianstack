> 在面栈阅读：[项目为什么这样实现，是否比较过其他方案和现有智能体？](https://mianstack.com/question/q-3246)

## 回答思路

用一个关键决策讲清：业务有什么约束，可选方案分别怎样完成任务，当前选择解决了什么，又增加了什么成本，以及什么条件下应当换方案。比较成熟产品时，要把它配置到能正常处理同一任务，再比较结果。

以下沿用四个假设的行业二开案例，通用能力来自所列底座，业务适配为设计示例。文中的比较依据是方案结构与接口约定，尚未做同任务实测；各版最后给出可执行的对照方法。

## 门店经营分析助手（Python）

### 核心回答示例

> 这条路线选择先检索元数据，再生成 `SQL`，因为门店运营问的“净销售额”“华北门店”需要对应到指标定义、真实字段和门店范围，单有表结构还不够。
>
> 候选有三种：把完整表结构和业务定义交给模型；沿用电商问数的定向元数据检索；集成 `SQLBot`。表少、定义稳定时，第一种最省维护。这里选择第二种，是为了按问题组织字段、指标和取值，并保留中间结果，方便定位口径在哪一步丢失。`SQLBot` 已有表管理、表关联、`SQL` 示例和术语配置，同样值得作为集成候选。
>
> 这个选择的代价是要维护元数据、向量与取值索引，还会引入漏召回。关键指标没找全，后面的 `SQL` 即使能执行也可能错。如果完整上下文已经够用，就可以简化；如果 `SQLBot` 配好业务定义后满足同一批问题和访问范围要求，集成它也可能更划算。

### 为什么保留检索与合并这一层

完整表结构方案少了检索环节，但仍要提供业务含义、关联关系和指标口径。数据范围扩大后，无关表会占用输入；定向检索则把成本转成了候选召回、索引更新和结果合并。

电商问数用 `Qdrant` 检索字段与指标、`Elasticsearch` 检索取值，再从 `MySQL` 元数据补充信息。合并节点已经具备去重、补指标依赖和主外键等处理；门店增量主要是净销售额、退款日期归属、门店别名及执行范围。补齐候选表的连接字段，也不代表任意跨表问题都能找到正确连接路径。

选择 `SQLBot` 时，同样需要维护这些业务定义。其官方实践已给出表范围、关联关系、示例 `SQL` 和术语配置，不能把“能够配置指标”当成自建路线独有的优势。真正要比较的是：现有配置与集成接口能否表达所需规则，以及维护它们与维护自建链路分别要做多少工作。

当前问数底座通过 `SSE` 返回过程；首次 `SQL` 校验失败后进入纠错，纠错后直接执行，没有再次校验。执行层的门店限制、只读权限与纠错后复验需要分别落实，元数据检索不能替代这些控制。

### 同任务怎样验证

固定同一份数据库快照、指标定义、模型配置与只读访问范围，比较完整上下文、自建检索和 `SQLBot` 三条路线。给 `SQLBot` 配置同等的字段说明、关联、术语和示例；记录各自的配置与开发投入，避免只让一方带着业务知识参测。

问题覆盖普通汇总、跨表关联、门店别名、退款跨月、同比日期，以及无权访问的门店。以人工对照 `SQL` 和结果判断口径是否正确，再检查候选字段、输入长度、端到端耗时与维护改动。对多种等价 `SQL` 比较结果和业务条件，不要求字符串相同。若检索缩短了输入却漏掉关键字段，就不能据此认定选型成功。

## 设备售后知识助手（Java）

### 核心回答示例

> 这个场景先选择 `Java` 固定知识问答链，因为售后工程师主要是确认设备后查适用手册，处理顺序比较稳定，而型号、版本和手册生效范围需要明确控制。
>
> 候选包括 `Ragent` 的固定 RAG 流程、动态 Agent，以及集成 `RAGFlow` 这样的知识平台。选择固定流程，是因为设备档案在 `Java` 业务系统中，匹配出的资料范围可以沿检索、重排和引用一路检查，问题也容易按步骤回放。动态 Agent 更适合需要根据查询结果继续查工单、调用其他系统的任务；平台集成则能复用知识管理与检索，但仍需对接设备规则。
>
> 代价是新增处理分支时要改代码，还要维护检索与模型服务的接入。如果业务从“查手册”扩展为多步排障和工单协办，就应重新评估 Agent；如果主要需求是文档管理和问答，平台配置已能满足设备范围，集成平台可以减少自建维护。

### 固定流程与动态决策分别解决什么

这条固定链路先由业务模块核对型号、版本，输出允许检索的手册或补问条件，再完成检索与生成。它的优势来自处理顺序可检查，而不是固定流程天然回答更准。文档选错、切分不当或证据不足，同样会答错。

`Ragent` `ff93871` 同时保留固定 Workflow 和基于 `AgentScope` 的 Agent 链路。若换成 Agent，可以让模型依据工具结果决定下一步，但设备范围仍由业务服务和检索层执行。底座的意图路由可能补充检索其他知识库，也可能回退到全局检索，不能把意图命中范围直接当成设备版本限制。采用 `Java` 服务路线，需要把设备条件接入各实际召回通道；接口中有过滤字段声明，也不代表通道已经执行了过滤。

动态调用还会累积工具说明、调用记录和工具结果，需要管理轮数、上下文和失败状态。为一个已知顺序的手册查询增加这种决策成本，是否值得，应由任务结果决定。反过来，如果必须先查设备状态，再按结果决定查哪种资料，硬编码越来越多分支也会成为负担。

集成 `RAGFlow` 是另一种工程分工：平台承担文档与检索，`Java` 服务保留设备匹配和业务接口。要核对平台当前版本的过滤与引用接口能否承接需求，再比较适配和运维成本，不能仅凭没有阅读相关接口就断言平台做不到。

### 同任务怎样验证

让固定 Workflow、`Ragent` Agent 与平台问答使用相同手册、设备档案、模型和问题集。平台路线补上同等的设备范围适配，Agent 路线提供同等的只读工具；配置无法完全一致的部分单独记录。

用同故障不同型号、新旧版本冲突、型号缺失和无适用资料检查：是否正确补问，所有召回与补充检索是否遵守范围，引用是否支持建议。再加入“查设备状态后决定下一步”的任务，观察固定流程需要增加哪些分支、Agent 是否选对工具和参数，同时记录调用次数、耗时及失败明细。这样才能判断动态决策是否带来值得承担的收益。

## 产业情报研读平台（Python）

### 核心回答示例

> 这个项目选择主智能体加来源助手，因为同一研究任务可能同时用到公开网页、业务数据库、内部知识库和上传材料，各类来源的查询规则不同，最后还要汇总成能回看出处的报告。
>
> 候选是单 Agent 顺序调用全部工具、深度研搜的来源分工，以及 `DeerFlow`。来源分工让网络、数据库和知识库助手分别处理自己的查询过程，主智能体集中组织结论。选择它的依据是现有 `Python` 服务已有这些接口，可以把企业别名、证据日期、转载去重和结论关联放在来源产物与报告之间。
>
> 代价是多了委派、交接和汇总，助手若漏掉原文位置，主智能体也难以补回证据。只有一份短材料时，单 Agent 更简单。如果任务进一步需要通用文件操作、代码执行和更完整的长任务运行环境，就应评估 `DeerFlow` 的集成成本与已有能力，而不是继续逐项自建。

### 为什么分来源，而不是只增加 Agent 数量

单 Agent 的好处是信息集中，不必维护助手间的交接；代价是所有工具说明和查询过程都进入同一上下文。来源助手则可以保留各自的工具与查询规则，向主智能体交回相关结果，但会增加模型调用，也可能在摘要中丢失细节。是否并行、是否更快或更准确，都不能由助手数量推出。

当前深度研搜底座由主智能体调用网络、数据库和 `RAGFlow` 三个助手，上传文件读取、`Markdown` 与 `PDF` 生成工具由主智能体掌握。行业增量是将来源、事实时间、原文位置与结论关联，处理转载和冲突。现有 `RAGFlow` 工具只把回答文本交回主智能体，未输出结构化来源；要保留证据，需要扩展工具输出或接入片段检索，而不是直接从回答文本推断原文位置。

`DeerFlow` 对照需要固定代际。本例参考的 `60940ae` 架构属于 2.0：它定位为包含子 Agent、记忆、沙箱和 Skills 的通用 Harness，官方明确说明它是对旧 Deep Research 框架的重写。它可以是承载研究任务的候选，但不能把旧版深研搜的流程与新版运行能力拼成一个方案。

采用现有底座还保留一项具体限制：进度经 `WebSocket` 返回，检查点使用 `InMemorySaver`。报告文件落盘不代表进程重启后可以继续任务。若业务要求长任务重启恢复，需要补持久化与恢复验证，或将该要求纳入成熟方案的对照。

### 同任务怎样验证

选择同一研究题目、截止日期和材料快照，给单 Agent、来源助手方案与所选 `DeerFlow` 版本提供等价的查询工具和访问范围。优先回放固定的搜索、数据库与知识库结果，排除网络内容变化；再单独做开放网络任务，记录实际取得的来源与调用预算。

任务包括单来源摘要、多来源互证、同名企业、不同事实日期、重复转载和冲突结论。逐条检查关键子问题是否覆盖、引用是否支持结论、时间是否一致、分歧是否保留，再比较耗时、模型用量和交接丢失。新增一份材料后，检查能否定位受影响结论；长任务另测取消、断连和服务重启。报告篇幅、来源数量和工具调用次数都不直接代表研究质量。

## 设备售后知识助手（RAGFlow 集成）

### 核心回答示例

> 这个版本选择 `RAGFlow` 加外部 `Python` 业务服务，因为文档解析、切分和检索可以复用平台，而每次请求允许使用哪些手册，要根据设备型号和版本确定。
>
> 对照路线是直接使用平台聊天入口、按设备系列或兼容版本分库，以及由业务服务代理受限检索。这里选择第三种：业务服务把设备映射为适用文档，调用检索接口，只把核对后的片段交给生成环节。这样可以检查每次请求的资料范围，也便于在没有适用手册时停止。
>
> 代价是要自己维护设备映射、接口适配、生成上下文和引用，还会受平台接口变化影响。设备系列少、兼容关系稳定时，分库后直接用平台聊天可能更省事；型号和版本组合多、共享手册多时，分库会增加资料复制和同步成本，文档级映射更值得考虑。

### 为什么不直接复用聊天入口

平台聊天入口可以复用助手配置、会话和回答生成，集成工作通常更少。关键是助手绑定的知识库及所选接口约束，能否准确表达本次设备的适用资料；这需要检查具体版本与配置，不能把平台统一描述为“没有过滤能力”。

本例依据 `RAGFlow` `v0.27.2`：片段检索接口支持 `dataset_ids` 和 `document_ids`，可以把设备匹配结果落实为检索范围，并返回来源文档与位置。外部 `Python` 服务维护设备与手册的对应关系，核对响应仍在范围内，再组织生成输入。设备匹配为空时直接返回资料缺口，避免把空文档列表当成“禁止检索”继续调用。

聊天接口有自己的助手配置和参数，不能直接套用片段检索的 `document_ids` 契约。若采用按设备系列与兼容版本拆库的路线，就要验证助手绑定确实满足范围，同时承担共享手册多处更新、兼容关系变更和助手配置同步的成本。

选择外部代理也不是消除了这些工作：它把资料适用规则集中到业务映射，换来了业务服务的开发与维护。若平台某个已核实的接口能够直接表达相同规则，就应重新比较继续保留代理是否划算。

### 同任务怎样验证

在相同版本、手册、解析结果和模型配置下，对照平台聊天、分库聊天与外部检索代理。前两条路线配置正确的助手和资料范围，代理路线记录设备映射、检索请求、返回片段和生成输入。

同一故障分别输入不同型号，再测试旧固件、缺少版本、共享手册更新和无适用资料。先判断资料范围是否正确，再判断证据是否足够、引用是否支持建议；同时记录一次手册更新要修改多少处配置、哪些请求受影响。把问答质量与资料维护成本一起比较，才能回答为什么采用这条集成路线。
