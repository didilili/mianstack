> 在面栈阅读：[LangGraph 的核心机制、作用与优缺点是什么？](https://mianstack.com/question/q-0862)

## 核心回答

LangGraph 是面向**有状态、多步骤任务的编排框架与运行时**。它把流程表示成图：State 保存当前数据，Node 读取状态并执行模型、工具或普通代码，Edge 决定下一步，Reducer 定义各字段怎样合并更新。定义后编译成可执行图，运行时推进分支、循环和并行步骤。

它的价值是把任务进度和控制流显式化，并能结合检查点、人工中断、流式输出和子图支持较长流程。比如“分析销量并形成报告”，可以明确哪些条件不足要澄清、哪些资料可以并行获取、哪些结果到齐后才汇总。

优点是流程可控、状态与失败位置较容易定位，适合分支多、需要暂停恢复的任务。代价是要维护状态 Schema、合并与路由规则、检查点及版本兼容；节点重跑时的业务幂等也需要应用处理。简单线性调用未必需要引入这层抽象，LangGraph 也不会自动提高模型判断或工具结果的正确性。

## 展开说明

### 1. 核心机制是图结构与状态更新共同工作

**State** 是当前运行数据的契约，可以包含请求、已确认条件、消息、工具结果和重试次数。**Node** 是执行函数，通常返回本次更新的字段；它可以调用模型、查询数据或做确定性校验，不要求每个节点都是一个 Agent。**Edge** 负责顺序转移或按状态选择分支，也可以形成循环。

同一个字段怎样更新由 Reducer 决定：默认更新通常覆盖旧值，累积列表可以配置相应合并函数。并行节点若都写同一个字段，必须设计适当的合并规则或分开结果槽；不能指望把两个赋值自动拼成正确答案。消息合并和业务结论合并也不是同一件事，最终口径仍需应用校验。

构建时可以用 `StateGraph` 定义状态、加入节点和边，再 `compile`。编译进行基础结构检查并配置运行参数，不验证每个业务判断。`TypedDict` 表达字段类型也不等于每份模型输出都会自动通过完整的运行时或业务校验。

运行算法按离散的 **super-step** 推进：本轮被调度的节点执行并提交更新，后续步骤根据状态继续。可以并行执行的节点属于同一轮调度；是否真正并行以及怎样等待依赖，取决于图的连接和调用方式，不能仅从使用 `astream` 推断所有任务都并行了。

### 2. 动态决策怎样放进图里

图可以固定关键步骤，同时让某些节点由模型判断下一步。比如意图节点输出已登记的分类，条件边据此选择数据查询或文档检索；结果不足时进入补查，完成或到达预算时结束。

如果需要同时更新状态和选择后续节点，可以在节点返回 `Command`；运行时才知道子任务数量时，可以通过 `Send` 为不同输入分派同类节点。它们表达的是动态控制与分派，目标、允许的路径和结果契约仍由开发者设计。

研搜参考项目通过 Deep Agents 使用 LangGraph 运行时，在主 Agent 入口配置检查点、`thread_id` 和流式执行，模型选择业务专家及工具。若业务需要更明确地控制澄清、查询、验证与交付顺序，也可以进一步把这些阶段建成显式节点和条件边。

### 3. 主要优点对应哪些需求

- **控制流清楚**：条件、循环、依赖和终止可以落到代码与状态，便于表达需要稳定顺序的业务步骤。
- **状态便于检查和复用**：中间结果、错误和下一步可以明确读取，调试时能定位到具体节点，而不只看到一大段最终对话。
- **支持较长任务**：配置合适的 checkpointer 和稳定线程标识后，可保存进度，结合中断等待用户输入，再按框架契约恢复；子图也能封装可复用流程。
- **易于接入过程输出**：可以输出节点更新、模型消息或自定义事件，再由应用对接前端和监控，让用户看到任务进展。

这些能力对复杂任务有帮助，但需按业务配置。例如需要进程重启后恢复，就要使用持久化检查点后端；研搜当前的 `InMemorySaver` 用于同一进程内保存上下文。

### 4. 主要代价与限制

首先是状态和路由维护成本。字段越来越多、Reducer 选择不当、静态边和动态路由混用，都可能导致重复执行或错误归并。图能展示控制结构，但不会自动把业务拆成合理节点；一个节点包揽全部逻辑时，仍然很难调试。

其次是持久化与恢复的成本。检查点会带来序列化、存储和 I/O 开销，大对象和不断增长的消息历史需要管理；具体持久化方式也影响崩溃时能保留多少进度。升级状态、工具和节点实现时，还应验证历史任务能否继续。

再次是外部副作用。恢复可能从节点开头重跑，检查点不能让远端数据库提交或邮件发送自动回滚。写操作需要业务幂等、回执核对和适当补偿，超时也不表示外部动作一定没发生。详细恢复设计可看[中断后如何继续任务](/question/q-0965/)。

最后是能力边界。流程控制解决的是怎样执行和保存进度；模型是否理解问题、检索证据是否可靠、业务权限是否正确，仍由模型、数据、工具和应用设计共同决定。选型时应结合任务质量、开发维护成本和延迟评测，不能单凭“支持图和检查点”判断一定值得使用。

## 常见追问

### LangGraph 和 LangChain 是替代关系吗？

可以组合。LangChain 提供模型、工具和 Agent 等较高层接口，LangGraph 提供有状态图执行能力；LangChain 的 Agent 也可以使用 LangGraph 运行时。需要更多控制时，可以直接设计图或将已有 Agent 放进图节点，具体取决于业务需要。

### 框架里的 Agent 怎么“自由发挥”？

通常是模型在某个节点内根据状态选择工具、提出子目标或给出路由结果，随后运行时按合法动作和路径执行。动态决策发生在应用定义的能力范围内，图仍控制关键检查、状态更新和退出条件。

### 什么时候不用 LangGraph？

如果流程只有少量固定调用，没有复杂分支、共享状态或暂停恢复需求，普通函数或轻量工作流可能更直接。可以先实现清楚的节点输入输出，等控制与恢复需求增加时再决定是否引入图运行时。
