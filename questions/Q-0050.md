## 核心回答

可靠的工具调用需要把**工具定义、参数校验、受控执行和结果反馈**连成闭环。模型根据上下文提出调用，应用负责验证、执行，并把真实结果交回模型。

1. **定义清楚**：说明工具用途、适用条件、输入字段和返回内容，让模型知道何时该用、需要提供什么。
2. **校验参数**：既检查类型、必填项等结构，也核对对象、时间和参数来源。凭证、用户身份和权限范围由应用提供与检查。
3. **受控执行**：只调用允许的工具，设置超时与调用上限，按原因决定补问、有限重试或停止。下单等写操作超时后，要先确认执行状态，或使用服务端支持的幂等机制，避免重复操作。
4. **反馈并确认结果**：成功返回真实数据，失败返回具体原因和可修正的信息，再检查结果是否满足任务。参数生成成功、HTTP 返回成功，都不等于任务完成。

例如用户问“这里明天会下雨吗”，系统却只有即时天气工具，就要先澄清城市，并说明当前工具不提供明天预报；即使生成了合法的北京参数，也还没有回答用户的问题。

## 用一个天气请求走完四道关

用户问：“这里明天会下雨吗？”假设系统只有 `get_weather(loc)`，且它只能查询即时天气。

**第一道关：工具是否适合这件事。** 工具名称和描述应写明用途、适用条件、输入含义及返回内容。工具很多时，可以先按当前任务筛选候选，让模型在相关能力里选择。这个请求既缺城市，又要求明天的预报：即使模型填出 `{"loc":"Beijing"}`，格式完全合法，调用仍然不符合用户意图。正确做法是先澄清地点，同时说明当前工具不提供明天预报；若系统另有预报工具，再按其要求调用。

**第二道关：参数是否有依据。** 用户改成“查北京现在的天气”后，城市才有明确来源。参数 schema 是一份结构约定，规定字段类型、必填项、范围或枚举。能用枚举表达的选项尽量少让模型自由编写；执行前再由程序验证格式和业务含义。在 LangChain 中，可以通过工具的 `args_schema` 绑定 Pydantic 参数模型。Pydantic 默认可能做类型转换，需要严格类型时应显式设置。城市名通过字符串校验后，同名城市仍可能需要消歧；对位置精度要求较高时，可以先地理编码，再用经纬度查询。

同时缩小模型需要决定的范围：天气工具里的摄氏度单位、中文语言和环境中的 API 凭证由代码设置。业务工具里的登录用户、租户、可操作范围也应来自可信上下文，而不是让模型填写后直接相信。

**第三道关：执行是否受控。** 应用只调用允许的工具，校验通过后再访问外部服务，并设置超时与调用上限。关键不是“失败都重试”，而是区分下一步：

| 得到的反馈             | 接下来怎么处理                       | 原因                                   |
| ---------------------- | ------------------------------------ | -------------------------------------- |
| 城市有多个候选         | 向用户确认地区                       | 猜一个候选可能查到真实但错误对象的数据 |
| 临时超时或限流         | 符合重试条件时退避，限制次数和总耗时 | 同参数重试可能恢复，但无限循环没有收益 |
| API 凭证无效或权限不足 | 停止调用，交给应用处理               | 让模型换城市不能修复身份问题           |
| 返回成功但没有温度字段 | 按不完整结果处理                     | HTTP 成功不等于满足业务所需            |

**第四道关：让反馈真正影响回答。** 成功就把真实天气结果交回模型；失败则返回错误类别、具体字段及可采取的下一步，例如“城市有多个候选，请补充省份”。在 LangChain 的通用 Tool Calling 消息流中，用 `ToolMessage.tool_call_id` 关联原请求。模型再根据反馈补问、修正或结束；没有取得天气数据，就不能生成相应的天气结论。

如果同一轮并行查询北京和上海，上海先返回，不能把第一个结果直接配给第一个请求。应用要按原调用 ID 关联结果，保留对应的工具名和参数；成功与失败也分别反馈。否则两个请求的参数都正确，模型最后仍可能把上海的天气当成北京的天气。

运行时还应记录工具名、脱敏后的参数、耗时和错误类别。这样才能分清是选错工具、参数推断错误，还是外部服务故障，并分别改工具说明、校验逻辑或执行策略。

## 追问

**用了严格结构输出，为什么还需要校验？**

模型接口支持的严格结构约束可以减少漏字段和错类型，但只约束规定的结构。`loc="Shanghai"` 完全可能通过 schema，却与用户要求的北京不一致。对象是否正确、时间是否合适、调用者是否有权限，仍要结合请求和业务状态判断。

**如果把天气查询换成下单，超时后还能直接重试吗？**

不能照搬。查询通常不改变业务状态，下单超时却可能是“订单已经创建，只是响应没回来”。需要先查执行状态，或使用服务端支持的幂等键，让同一业务请求重试时不重复创建；幂等键应由应用管理，不能每次让模型另生成一个。

**怎么证明改动让调用更可靠？**

用一组具体请求分别检查工具选择、参数含义和最终结果。除了正常查北京，还要放入“这里天气”“明天天气”、无权限、超时、结果缺字段等样例。应补问时没有乱调、服务失败时没有编结果，同样属于正确表现；只统计 JSON 解析成功率会漏掉这些问题。
